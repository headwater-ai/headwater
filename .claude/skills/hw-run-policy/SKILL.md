# The run policy

Every stage of a build-order run reads this once. It cites a ruling rather than restating it, and the value rule is stated once in `.claude/commands/next-run.md` and nowhere else.

## The standing rulings

- **A stale premise is adjudicated; nobody halts.** The adjudicator refuses with what changed, the parent rules, and the human hears of it only when a redirect changes milestone order or a decision needs an owner ([HW-PD-0002](../../../docs/process/decisions/0002-adjudication-is-a-separate-stage-and-refusal-is-licensed.md)).
- **Refusal has three kinds, and the parent rules on the kind.** "Nothing states what this is" ships a verb that reports the gap and merges. "This would be better done another way" is a product decision, merged only if reversible and recorded with the condition that reopens it, written into the artifact where the next reader meets it. "The Done-when offers a second outcome and the measurement says take it" is a completion ([HW-PD-0002](../../../docs/process/decisions/0002-adjudication-is-a-separate-stage-and-refusal-is-licensed.md)).
- **An honest split is a success condition.** `Refs #N` with a measured reason beats `Closes #N` on a bar that was stretched. When declines cluster, write smaller issues rather than praising the split.
- **A recorded blocker is not a measured one.** Re-measure a blocker before inheriting it.
- **A milestone can run out of buildable work without being finished**, and that is a finding: say what each remaining issue waits on, leave the epic open, and move on without manufacturing work.
- **The board's structure is the product owner's, and its scope is the parent's.** `.claude/agents/headwater-product-owner.md` closes a finished milestone, moves a misfiled issue, writes the priority labels, closes an epic under the test its definition states, and posts the owner's rulings to their issues; nobody else does in passing.
- **A finding with no reader outside this repository goes to spec 13, capped at three per iteration**, past which one obligation record lists the rest. The register is hand-maintained and its own count has gone stale by hand ([HW-OBL-0142](../../../docs/obligations/0142-the-obligation-register-states-its-own-size-by-hand-and-it-went-stale-three-times-in-two-days.md)).
- **The owner's rulings are asked at the top of a run, and a deferral is an answer.** `headwater-product-owner` writes one `RULING` block for each decision the owner owes, in its report and in `rulings.md` in the run directory. The parent puts every block to the owner before it fills the first slot, with `AskUserQuestion`, the recommended option first and `Defer` last, four questions to a call. The parent records each answer at once in the run's `decisions.md` with `sh tools/run/run-dir.sh decide`, as one line whose text opens `OWNER (<date>) #<N>:` and quotes the owner's words. That line is the record the product owner posts to the issue and `hw-adjudicate` reads, and each definition says how. The line marked `ruling` in the queue is then ordinary work. A deferral goes into the run's decisions file and the line is skipped for this run alone. Where no person is in the session, every question counts as deferred, and the final report lists each one. No agent answers a question in the owner's place, and no issue that waits on the owner is passed over without one of these two records.
- **A closed version milestone is a prompt, never a tag.** When the product owner's report opens with `RELEASE READY`, the parent asks the owner whether to cut the release, in the same way as a ruling. A session pushes the tag only on the owner's yes in that session, and `hw-integrate` never does.
- **No stage files an issue inside a run.** A finding that is not the issue in hand is one line appended to `intake.md` in the run directory: `printf '%s\n' '- #<issue in hand> | <stage> | <what is wrong, with the path> | <the reader outside this repository, or none>' >> <run>/intake.md`. `headwater-product-owner` rules on every line at its next pass, and its definition names the four rulings. It runs every fifth merge and at the end, so a question for it is an intake line too, never a decisions note. The cap of three above still holds for what it sends to spec 13. A finding that blocks the issue in hand is not intake: it goes in your report, and the parent rules on it.
- **Every issue filed or edited opens with an `## ELI5` section**, per `.github/ISSUE_TEMPLATE/issue.md`, which `gh` does not apply.
- **A red `main` is fixed in the next iteration's branch before that iteration's own work.**
- **An agent that dies is resumed by its id, never replaced.** Only pushed commits survive. The one exception is a parent restart: every subagent dies with its parent's process, so no id is left to resume, and the handover file stands in for it ([HW-PD-0023](../../../docs/process/decisions/0023-a-build-order-parent-restarts-every-few-merges-drains-to-zero-first-and-resumes-from-the-handover-files-on-disk.md)).
- **A parent restarts every few merges, and drains to zero first** ([HW-PD-0023](../../../docs/process/decisions/0023-a-build-order-parent-restarts-every-few-merges-drains-to-zero-first-and-resumes-from-the-handover-files-on-disk.md)). `tools/run/supervise.sh` runs each session after the first and creates `<run>/drain`, and its header states the thresholds and the measurement behind them. The state a restart keeps is `sh tools/run/run-dir.sh`, and its verbs are the only way to write it:
  - **At each stage boundary, write the checkpoint.** The parent runs `run-dir.sh stage <run> <issue> adjudicated note=<path> branch=<name> footprint=<a,b>` on a `BUILD` report, before it claims. `hw-iterate` writes `built`, `verified-fail` and `verified-pass`. The parent writes `ruled-merge` when it rules a merge. Record a refusal, a deferral, a gate or the lifting of one with `run-dir.sh rule <run> <issue> gated|deferred|refused|open <reason>`, because `next` reads that line and not the prose around it. A `RULED` line names its run and binds that run alone, so a deferral does not outlive it, although `start` seeds the next run's `decisions.md` with it. An `OWNER` line is the deliberate difference: it is the owner's answer, posted on the issue, so it answers a `ruling` queue line in every later run as well.
  - **A veto after a restart.** When the `hw-iterate` that reported a `PASS` is gone, write the veto to a file and run `run-dir.sh stage <run> <issue> verified-fail verify=<veto file>`. Every field the call does not name carries from the checkpoint before, and `resume` then prints `iterate`, the path a verify `FAIL` already takes.
  - **In drain**, `claim`, `stage`, `next` and `resume` print `DRAIN`. Start no new stage: dispatch no adjudicate, no `hw-iterate` and no integrator. `claim` writes nothing, so an adjudicate that reports in drain stays staged `adjudicated`, and the next session claims it. An `hw-iterate` in flight writes its checkpoint at its next stage boundary and returns `VERDICT: HANDOVER`, which needs nothing from you: its checkpoint is on disk. Rule a `PASS` that arrives, and append it to the integrator queue. Let an integrator in flight finish. Exit when nothing is in flight.
  - **A resumed parent** runs `run-dir.sh session <run>` first, so the review hook knows it. Then it reads the doctrine, `run-dir.sh tail <run>` and `run-dir.sh resume <run>`, and nothing else of the ledger. For each line of `resume`: `claim <artifacts>` means claim, then dispatch `hw-iterate` with the handover path, and it starts from the adjudication note; `iterate` means dispatch a fresh `hw-iterate` with the handover path; `rule` means rule the `PASS` from the notes the handover names; `integrate` means append the ruling to the integrator queue. Then fill from `run-dir.sh next`.
- **An agent can state a write-back and not land it.** Read what it did, never what it said it would do, and check the board after every resume.
- **The loop for one issue runs below the parent, and the parent never reads a build branch.** `hw-iterate` owns build, verify and rework and reports once. The parent rules from that report and the notes it names, and never runs `git show` or `git diff` against a build branch ([HW-PD-0022](../../../docs/process/decisions/0022-the-verify-and-rework-loop-for-one-issue-runs-below-the-parent.md)).
- **Coordination is a claim on the board or a create-only file, never a coordinator's context** ([HW-PD-0004](../../../docs/process/decisions/0004-coordination-is-a-create-only-claim-and-authority-stays-on-the-tree.md)). The veto and the re-verify travel by `SendMessage`; authority stays on the tree.
- **Never run a generating verb against a checkout another session is merging into.** Two sessions regenerating a corpus-wide artifact do not conflict, because blobs are compared before a merge strategy is chosen; they merge wrong ([HW-DR-0049](../../../docs/decisions/0049-a-corpus-wide-fold-is-derived-and-never-stored.md)).

## The environment

Each entry cost somebody an hour.

- `gh issue view` and `gh pr edit` fail on this repository. Read and write a single issue through `sh tools/run/gh-issue.sh`, whose header says why.
- Move a board card with `sh tools/run/board-move.sh <N> todo|in-progress|done`, never a hand-typed `gh project` call. If `gh project` refuses, the token lacks the `project` scope, and only a human can grant it, with `gh auth refresh -s project,read:project`.
- Every wait on CI is `sh tools/run/wait-for.sh 'sh tools/run/ci-done.sh <sha>'`, which ends on `green` or on `red` with the failures named. Its header records the conditions it replaced and why each was wrong.
- Every wait on the merge queue is `sh tools/run/wait-for.sh 'sh tools/run/queue-done.sh <PR>'`, which ends on `merged`, on `ejected` with GitHub's reason, on `closed`, or on `not queued` ([HW-PD-0020](../../../docs/process/decisions/0020-merges-go-through-the-github-merge-queue-one-squash-commit-per-pull-request.md)).
- Worktree isolation refuses heredocs, compound shell, `git -C` into another worktree, a script fed through a heredoc that names git, and `trap` in any shape, whatever the command underneath. Write scripts to files and run them.
- `Write` is refused in the shared checkout and `EnterWorktree` is refused from a subagent. A subagent that needs its own tree gets it at launch: `hw-iterate` dispatches `hw-build` and `hw-verify` with the Agent tool's `isolation: "worktree"`, and the agent works in a tree the harness makes for it under the worktrees directory, named for the agent, with git, `Write` and `Edit` allowed there (measured 2026-09-26, #975 PR #1128; four builders ran at once this way). An agent launched this way does not run `new-worktree.sh`: it branches in place (`git switch -c <branch> origin/main`, or `--detach origin/<branch>` to verify) and builds the engine there with `sh tools/hw-cargo`. Keep git calls plain: a git call inside a `for` loop, a command substitution or a `;` sequence is refused, and a script file that runs the same loop passes. `&&` with git passes, and so does a redirect to a file: `cd <your tree> && git add <paths> && git commit > <file>` passed (measured 2026-09-28, #1276 and its verifier). A tree made by hand with `git worktree add` or `sh tools/repo/new-worktree.sh` is not one the agent's isolation allows, so `cd`, `git -C`, `Write` and `Edit` into it can be refused.
- A worktree-isolated parent reaches the run directory only through `sh tools/run/run-dir.sh` subcommands, and its shell refuses any command whose text names `.git`. So every subcommand takes a bare run id in place of the path, and `decide`, `intake`, `withdraw` and `lesson` write the prose ledger: `decisions.md`, `intake.md` and `lessons.md`. Write no script of your own for this.
- `git push -u origin <branch>`, never a bare push.
- `core.hooksPath` reads as an absolute path after any `EnterWorktree`. That is expected and runs the right hook; [DEVELOPING.md](../../../DEVELOPING.md) says why.
- **Every cargo command of a run goes through `sh tools/hw-cargo`**, with the same arguments you would have given cargo: `sh tools/hw-cargo build --profile dev-release -p headwater-cli --manifest-path engine/Cargo.toml --locked`, and the same wrapper for `test` and for `check`. A direct `cargo` is throttled by nothing; the script's header says what its slots and pooled target directories share. Never `--release` for a checked commit ([DEVELOPING.md](../../../DEVELOPING.md) says why), and never copy a binary between the two profiles' paths. `hw-integrate` and `headwater-maintainer` set `HW_CARGO_SLOT=integrate` and `maintainer`, and `hw-verify` sets `verify-<N>` for its issue, reserved slots outside the numbered pool. A maintainer that `hw-build` dispatches sets `maintainer-<N>` for the build's issue instead, for the reason the next sentence gives for verifiers, and removes that target when it reports. When more than one verifier runs at once, each sets `HW_CARGO_SLOT=verify-<N>` for its issue instead: two verifiers on the one `verify` slot share its target directory, and a test that did not rebuild the CLI copied the other tree's older `headwater` binary into the verifier's tree (measured 2026-09-26, #1096 and #953). Each such slot builds its own 10-13 GB target under `~/.cache/headwater/cargo-pool/`, and seven of them took the host's disk to 96% in one run, which the shared runner turns into a red ENOSPC CI. A verifier on its own slot therefore removes `target-verify-<N>` and its `.root` file when it reports, and `hw-iterate` checks `df -h /` before it dispatches a verify.
- **Never run clippy locally. It is CI's gate and not a stage's.** It compiles the whole workspace again under a second toolchain, and [DEVELOPING.md](../../../DEVELOPING.md) rules that a green clippy on your host is not evidence about CI. Push and read CI.
- **Rebuild the engine after a rebase or a merge, before `headwater generate` or `headwater check`.** A pre-rebase binary writes stale artifacts and passes them, because the same binary wrote and checked them; and a stale binary reads correct pages as stale, with a destructive remedy. Read the direction of the delta before believing either.
- **Never pipe a gate.** `<gate> | <filter>` reports the filter's exit status. Redirect to a file and read the tail in a second call.
- **Never merge stderr into stdout on an invariant test.** The engine prints a run statistic to stderr and the artifact to stdout, and one agent wrote "the cache invariant is literally false" into durable memory on the strength of `2>&1`.
- **A test of the engine re-resolves the lock.** `headwater check` takes its taxonomy from `.headwater/taxonomy.lock` alone. Since #1186 it also hashes the vendored package under `.headwater/packages/` against its digest pin, so a hand edit there fails `taxonomy.pin.diverged` rather than passing. Run `headwater taxonomy resolve` between editing `.headwater/packages/` and checking, and resolve after publishing, not before, or both sides of a comparison move together.
- A conflicting pull request runs no CI at all. Read `mergeable` before reading a missing check run as a dead runner.
- `cargo` runs a target's cases as threads of one process, so a temp-dir helper keyed on the pid alone races, and the symptom is `NotFound` out of `std::fs::copy`.
- A cargo failure quoting a dead worktree's path is an `sccache` hit rather than a defect; `cargo clean -p <crate>` clears it.
- **`cargo clean -p <crate>` is profile-scoped.** Cleaning the default profile leaves `dev-release`'s own build products alone, so a stale `dev-release` rlib from a concurrent agent's older source on the same shared `tools/hw-cargo` pool survives a clean that looks complete, and a rebuild then reports "method not found" against code plainly on disk. Pass `--profile dev-release` too: `cargo clean -p <crate> --profile dev-release`.
- Never navigate from rust-analyzer's `documentSymbol` line numbers; `grep -n 'fn <name>'` first.
- `tools/hw-cargo` waits on slot 1 alone when all three are busy. Probe the three lock files with `(flock -n 9; ...) 9>>file` and take a free one with the same pool path, target dir, job cap and nice level. The bare `flock -n 9 -c ... 9>>file` form treats `9` as a filename. Delete this line when `tools/hw-cargo` is fixed.
- **A slot held by a process with no build behind it is yours to free.** Before 2026-09-24 `tools/hw-cargo` leaked its lock into the `sccache` server, and a server started then can still hold a slot until it idles out. `fuser <pool>/slot.<n>.lock` names the holders. Kill an `sccache` server, or a queued `hw-cargo` whose caller has exited, after checking it is not a live build of another stage, and say in your report what you killed. The owner ruled on 2026-09-23 that a stage does this itself rather than handing the human a `kill` line.
- Commit and push in small steps. A transport error costs everything unbanked.

## The same list, read for cost

A tool result costs its own size times the turns that follow it, so position is worth as much as size ([HW-PD-0003](../../../docs/process/decisions/0003-a-dispatch-pays-when-it-retires-more-parent-turns-than-it-costs.md)).

- **Wait by blocking in the foreground, never by polling and never by ending your turn.** `sh tools/run/wait-for.sh '<condition-command>'`, run in the foreground with a Bash `timeout` of `300000`, is one call that polls every thirty seconds and ends inside four minutes, on the condition or on `RE-ISSUE`. On `RE-ISSUE`, run the identical call again: that attempt has ended. Never start a wait with `run_in_background: true`. A stage whose only work left is a background wait ends its turn, and each attempt then wakes the parent at its full context to read a line that says nothing ([HW-PD-0021](../../../docs/process/decisions/0021-a-subagent-waits-in-the-foreground-because-a-background-wait-wakes-its-parent.md)). A long job that is not a wait, such as a build or a suite, still goes in the background, and `wait-for.sh` waits in the foreground on its exit marker. The stages that run `wait-for.sh` are `hw-build`, `hw-verify` and `hw-integrate`. Two agents wait on an agent and not on a condition, so they run no `wait-for.sh` and end their turn instead: `hw-iterate` waits on its builder and its verifier ([HW-PD-0022](../../../docs/process/decisions/0022-the-verify-and-rework-loop-for-one-issue-runs-below-the-parent.md)), and the parent waits on its stages. A bare re-check, a `sleep <n> && <check>` turn and `Monitor` on a build that finishes once are all polls. The script's header, [HW-PD-0007](../../../docs/process/decisions/0007-a-background-wait-caps-below-the-cache-lifetime-and-re-issues-itself.md) and HW-PD-0021 carry what each shape cost.
- **A report is the fixed block and nothing before it.** Every stage writes its narrative to `<scratch>/<stage>-report.md` by shell redirect and returns the block its definition names; the parent opens the file only when ruling.
- **Backgrounding a job is half a decision; the other half is how you wait for it.** Decide both in the same breath, and end every wait you started before you exit — the last bounded call in a chain included, once the condition it names is met.
- **Redirect a build or a check to files and read the tail**, stdout and stderr to separate files. `sh tools/cap-run <command...>` does this in one call for a command that merges the two safely: it prints only the head, the tail, the omitted-line count, the exit status and the log's path, and keeps the whole run on disk. Do not reach for it on an invariant test that depends on reading stdout and stderr apart.
- **Ask an API for the field, never the record.** `gh api ... --jq .body` carries the one field you asked for.
- **Find the files before the lines, and read a range, never a source file.** `grep -rl` or `Glob` first, then `grep -n` in the few files that match. Read with `Read` and an offset and a limit, or `sed -n '<a>,<b>p'`, eighty lines at a time at most, and never `cat` a source file. Take a line range from the file on disk, never from memory or a symbol outline.
- **Never read a whole specification part.** `headwater explain` first, then `Read` with an offset and a limit.
- **Do not run the same command twice**, and count your repeats rather than trusting that you would notice.
- **Prefer `Edit` to `Write` on a file that exists**, and compose a long prompt or note in a file rather than in a shell argument.
- **Correct an environment claim the moment you disprove it**, in the place it was written.
- **No bound is set on the length of a build agent, and a builder past 200 turns goes on.** Over 120 builders, the length of a builder drove its late-turn cost and the size of its issue did not. A handoff at 200 turns could have saved at most 4.9% of the builders' cost since 2026-09-23, before the handoff paid for itself ([the evaluation](../../../docs/evaluations/the-build-order-as-a-multi-agent-system.md)). The finding opens again when, over the last five runs taken together, more than one builder in five passes 200 turns or the median growth of the builders passes 2x. On 2026-09-27 those five runs had 6 of 59 builders past 200 turns and a median growth of 1.5x, so the finding stands. The `growth` line of `sh tools/run/run-census.sh <transcript>` gives both figures for each builder.
