# The run policy

Every stage of a build-order run reads this once. It is a skill and not a paragraph in each definition because more than one stage obeys it ([HW-PD-0001](../../../docs/process/decisions/0001-orchestration-prose-has-one-owner-per-sentence.md)), and it cites a ruling rather than restating it so that a ruling tuned later moves in one place. The value rule is stated once in `.claude/commands/next-run.md` and nowhere else.

## The standing rulings

- **A stale premise is adjudicated; nobody halts.** The adjudicator refuses with what changed, the parent rules, and the human hears of it only when a redirect changes milestone order or a decision needs an owner ([HW-PD-0002](../../../docs/process/decisions/0002-adjudication-is-a-separate-stage-and-refusal-is-licensed.md)).
- **Refusal has three kinds, and the parent rules on the kind.** "Nothing states what this is" ships a verb that reports the gap and merges. "This would be better done another way" is a product decision, merged only if reversible and recorded with the condition that reopens it, written into the artifact where the next reader meets it. "The Done-when offers a second outcome and the measurement says take it" is a completion ([HW-PD-0002](../../../docs/process/decisions/0002-adjudication-is-a-separate-stage-and-refusal-is-licensed.md)).
- **An honest split is a success condition.** `Refs #N` with a measured reason beats `Closes #N` on a bar that was stretched. When declines cluster, write smaller issues rather than praising the split.
- **A recorded blocker is not a measured one.** Re-measure a blocker before inheriting it. Three times in one run a milestone or an issue sat on an assessment nobody had re-taken.
- **A milestone can run out of buildable work without being finished**, and that is a finding: say what each remaining issue waits on, leave the epic open, and move on without manufacturing work.
- **The board's structure is the product owner's, and its scope is the parent's.** `.claude/agents/headwater-product-owner.md` closes a finished milestone, moves a misfiled issue and writes the priority labels; nobody else does in passing. Closing an epic whose children are all done, after verifying its Done-when clause by clause, stays with the parent.
- **A finding with no reader outside this repository goes to spec 13, capped at three per iteration**, past which one obligation record lists the rest. The register is hand-maintained and its own count has gone stale by hand ([HW-OBL-0142](../../../docs/obligations/0142-the-obligation-register-states-its-own-size-by-hand-and-it-went-stale-three-times-in-two-days.md)).
- **The owner's rulings are asked at the top of a run, and a deferral is an answer.** `headwater-product-owner` writes one `RULING` block for each decision the owner owes, in its report and in `rulings.md` in the run directory. The parent puts every block to the owner before it fills the first slot, with `AskUserQuestion`, the recommended option first and `Defer` last, four questions to a call. An answer goes onto the issue as a comment that quotes the owner's words, `status:needs-ruling` comes off, and the line marked `ruling` in the queue is then ordinary work. A deferral goes into the run's decisions file and the line is skipped for this run alone. Where no person is in the session, every question counts as deferred, and the final report lists each one. No agent answers a question in the owner's place, and no issue that waits on the owner is passed over without one of these two records.
- **A closed version milestone is a prompt, never a tag.** When the product owner's report opens with `RELEASE READY`, the parent asks the owner whether to cut the release, in the same way as a ruling. A session pushes the tag only on the owner's yes in that session, and `hw-integrate` never does.
- **No stage files an issue inside a run.** A finding that is not the issue in hand is one line appended to `intake.md` in the run directory: `printf '%s\n' '- #<issue in hand> | <stage> | <what is wrong, with the path> | <the reader outside this repository, or none>' >> <run>/intake.md`. `headwater-product-owner` rules on every line at its next pass, and its definition names the four rulings. The cap of three above still holds for what it sends to spec 13. A finding that blocks the issue in hand is not intake: it goes in your report, and the parent rules on it.
- **Every issue filed or edited opens with an `## ELI5` section**, per `.github/ISSUE_TEMPLATE/issue.md`, which `gh` does not apply.
- **A red `main` is fixed in the next iteration's branch before that iteration's own work.**
- **An agent that dies is resumed by its id, never replaced.** A fresh agent throws away a settled design; both agents that died in one run finished their own work on resume. Only pushed commits survive.
- **An agent can state a write-back and not land it.** Read what it did, never what it said it would do, and check the board after every resume.
- **Coordination is a claim on the board or a create-only file, never a coordinator's context** ([HW-PD-0004](../../../docs/process/decisions/0004-coordination-is-a-create-only-claim-and-authority-stays-on-the-tree.md)). The veto and the re-verify travel by `SendMessage`; authority stays on the tree.
- **Never run a generating verb against a checkout another session is merging into.** Two sessions regenerating a corpus-wide artifact do not conflict, because blobs are compared before a merge strategy is chosen; they merge wrong ([HW-DR-0049](../../../docs/decisions/0049-a-corpus-wide-fold-is-derived-and-never-stored.md)).

## The environment

Each entry cost somebody an hour.

- `gh issue view` and `gh pr edit` fail with a `projectCards` GraphQL deprecation. `tools/run/gh-issue.sh` carries the working form of every read and write this repository makes against a single issue — body, comments, a body patch, a new comment, a close that confirms it took — so that the endpoint and the `--jq` filter are retyped in one place rather than at every call site.
- This repository's classic Projects REST API 404s even with `has_projects: true` — GitHub deprecated it platform-wide; use the `gh project` CLI (Projects v2 / GraphQL) instead. Two independent build agents hit this on 2026-09-20 (#435, #601) as a `gh` token missing `project`/`read:project` scope, which made `gh project list` itself refuse; the owner ran `gh auth refresh -s project,read:project` interactively the same day and it now works from every session on this host. If `gh project list` ever refuses again, that scope is what to check first, and the fix needs a human's interactive browser device-code flow — no agent session can complete it itself.
  To move an issue's board card (claim through the board, per `hw-build.md`): `sh tools/run/board-move.sh <N> todo|in-progress|done`. It resolves the issue to its item id and sends the option id for that status; both are opaque strings nothing derives, and the project's own README says its Status field is the one thing here not derivable from the repository, so this is worth doing, not just assigning the issue. It adds the card when the issue has none yet.
- Every wait on CI is `sh tools/run/wait-for.sh 'sh tools/run/ci-done.sh <sha>'`, which ends on `green` or on `red` with the failures named. Its header records the conditions it replaced and why each was wrong.
- Worktree isolation refuses heredocs, compound shell, `git -C` into another worktree, a script fed through a heredoc that names git, and `trap` in any shape, unconditionally, whether or not the command underneath it was safe. Write scripts to files and run them; a hook that generated a `trap`-bearing command for a worktree-isolated session found this out the hard way and was replaced by `tools/cap-run`, a plain script a caller invokes by name instead.
- `Write` is refused in the shared checkout and `EnterWorktree` is refused from a subagent. `sh tools/repo/new-worktree.sh <path> <git-worktree-add-args>` fetches, adds and builds the engine there in one call, so a fresh worktree never sits without one; remove the tree at the end or say that it is still there.
- `git push -u origin <branch>`, never a bare push. The git setting push.default is `simple` on this machine now, and the explicit form is right under either setting.
- `git config --get core.hooksPath` answers an absolute path on every worktree, because `EnterWorktree` rewrites it that way on every call and never restores it. That no longer runs the wrong hook body: every `.githooks/` hook hands off to the copy under the worktree actually committing, whatever the value names ([#925](https://github.com/headwater-ai/headwater/issues/925), fixed by [#946](https://github.com/headwater-ai/headwater/pull/946)). Only a branch with no copy of that hook of its own still runs the checkout the value names, and the hook reports which case happened.
- Build with `cargo build --profile dev-release -p headwater-cli --manifest-path engine/Cargo.toml --locked`, never `--release` for a checked commit: the release profile's `lto` and single codegen unit are single threaded and cost minutes. The gate and every hook run whichever profile is newer. Never copy a binary between the two paths.
- **Every cargo command of a run goes through `sh tools/hw-cargo`**, with the same arguments you would have given cargo: `sh tools/hw-cargo build --profile dev-release -p headwater-cli --manifest-path engine/Cargo.toml --locked`, and the same wrapper for `test` and for `check`. It takes one of three slots and points cargo at that slot's pooled target directory, so the stages of a run share a compiled dependency graph instead of each rebuilding it, and the cap on concurrent compilers is a real one. A stage that calls cargo directly is not throttled by anything and competes with every other stage for the same eight cores. The header of the script carries the measurement that set both numbers. `hw-integrate` and `headwater-maintainer` set `HW_CARGO_SLOT=integrate` and `HW_CARGO_SLOT=maintainer`: a reserved, unnumbered slot that never queues behind a builder's and is never queued on by one, so throttling a stage that is not a builder does not shrink a run's build concurrency.
- **Never run clippy locally. It is CI's gate and not a stage's.** Clippy is the only tool a run reaches for that needs the rustup toolchain, so it compiles the whole workspace a second time under a second compiler and shares neither a fingerprint nor an sccache key with anything else the run builds. [DEVELOPING.md](../../../DEVELOPING.md) already rules that a green clippy on your host is not evidence about CI. Push and read CI.
- **Rebuild the engine after a rebase or a merge, before `headwater generate` or `headwater check`.** A pre-rebase binary writes stale artifacts and passes them, because the same binary wrote and checked them; and a stale binary reads correct pages as stale, with a destructive remedy. Read the direction of the delta before believing either.
- **Never pipe a gate.** `<gate> | <filter>` reports the filter's exit status. Redirect to a file and read the tail in a second call.
- **Never merge stderr into stdout on an invariant test.** The engine prints a run statistic to stderr and the artifact to stdout, and one agent wrote "the cache invariant is literally false" into durable memory on the strength of `2>&1`.
- **A test of the engine re-resolves the lock.** `headwater check` reads `.headwater/taxonomy.lock` and never the package sources. Run `headwater taxonomy resolve` between editing `.headwater/packages/` and checking, and resolve after publishing, not before, or both sides of a comparison move together.
- A conflicting pull request runs no CI at all. Read `mergeable` before reading a missing check run as a dead runner.
- `cargo` runs a target's cases as threads of one process, so a temp-dir helper keyed on the pid alone races, and the symptom is `NotFound` out of `std::fs::copy`.
- A cargo failure quoting a dead worktree's path is an `sccache` hit rather than a defect; `cargo clean -p <crate>` clears it. A fresh worktree has no engine, so the commit gate fails open there until you build one.
- **`cargo clean -p <crate>` is profile-scoped.** Cleaning the default profile leaves `dev-release`'s own build products alone, so a stale `dev-release` rlib from a concurrent agent's older source on the same shared `tools/hw-cargo` pool survives a clean that looks complete, and a rebuild then reports "method not found" against code plainly on disk. Pass `--profile dev-release` too: `cargo clean -p <crate> --profile dev-release`.
- Never navigate from rust-analyzer's `documentSymbol` line numbers; `grep -n 'fn <name>'` first.
- `tools/hw-cargo` waits on slot 1 alone when all three are busy. Probe the three lock files with `(flock -n 9; ...) 9>>file` and take a free one with the same pool path, target dir, job cap and nice level. The bare `flock -n 9 -c ... 9>>file` form treats `9` as a filename. Delete this line when `tools/hw-cargo` is fixed.
- **A slot held by a process with no build behind it is yours to free.** Before 2026-09-24 `tools/hw-cargo` leaked its lock into the `sccache` server, and a server started then can still hold a slot until it idles out. `fuser <pool>/slot.<n>.lock` names the holders. Kill an `sccache` server, or a queued `hw-cargo` whose caller has exited, after checking it is not a live build of another stage, and say in your report what you killed. The owner ruled on 2026-09-23 that a stage does this itself rather than handing the human a `kill` line.
- Commit and push in small steps. A transport error costs everything unbanked.

## The same list, read for cost

A tool result costs its own size times the turns that follow it, so position is worth as much as size ([HW-PD-0003](../../../docs/process/decisions/0003-a-dispatch-pays-when-it-retires-more-parent-turns-than-it-costs.md)).

- **Wait by blocking in the background, never by polling or in the foreground, and cap the block below the five-minute cache lifetime.** `sh tools/run/wait-for.sh '<condition-command>'` is one call that blocks, polls no sooner than every thirty seconds, and exits either because the condition held or because its cap (240 seconds, under the lifetime) was reached, in which case it says `RE-ISSUE` rather than swallowing the wait — never a bare re-check. Start it with `run_in_background: true` because a foreground call is capped at ten minutes and answers `moved to the background (ID: ...)` on its own, which reports nothing about the build. `Monitor` answers a different question, which is one notification per occurrence, and it is the wrong instrument for a single build that finishes once. One agent checked a status file 85 times in five minutes and burned 29% of a whole run; the parent of run 20260911-1331 ran a bare `true` 193 times and burned 55%; in run `cc7cc6c6`, 47 foreground waits reached the cap and spent 7.8 hours, a third of every shell call in the run. Those are the cost of polling and of the foreground cap. The other end of the cost is silence: a call backgrounded and left running to completion, however long that takes, wakes a turn whose prompt cache the harness has by then discarded, past about five minutes of nothing sent, and that turn pays to write the whole context back rather than to read it, at 1.25x the input rate against 0.1x. Run `9ab3be93` woke up thirteen times past that bound and paid $14.85 rewriting 5.94M tokens, where returning inside the lifetime would have cost about $3.84 ([HW-PD-0007](../../../docs/process/decisions/0007-a-background-wait-caps-below-the-cache-lifetime-and-re-issues-itself.md)). `tools/run/wait-for.sh` is that wrap: re-issue the identical call on a `RE-ISSUE` exit, because that attempt has genuinely ended by then, unlike a wait the harness itself only moved to the background at the ten-minute cap, which is still running and is never the one re-issued. The parent alone waits differently: it dispatches, then ends its turn, and each report wakes it at no cost, because the five-minute lifetime is a subagent's and not the parent's. Every transcript in this repository measured on 2026-09-21, 17 parents and 94 subagents, wrote its parent cache to the one-hour lifetime and its subagent cache to the five-minute one: 87 parent turns woke after a gap of five to sixty minutes and none paid a rewrite, where 33 of 35 subagent turns after the same gap did. **This is a build agent's own habit as much as the parent's.** Run `20260920-2058` measured it inside `hw-build` itself, not only at the top level: one builder issued twenty-one separate `sleep 5 && echo ok`-shaped turns waiting on its own CI run, at 5.9M cache-read tokens for those turns alone, where the `until`/`while` form above would have been one call. A bare `sleep <n> && <check>` is the same bare re-check the rule already names, wearing a delay; the fix is the same single blocking loop, not a shorter sleep.
- **A build agent that reruns the full suite each time it edits pays for the whole workspace on every turn.** Run `20260920-2058` measured one builder running `cargo test --workspace` eleven times over its own build, and another running `cargo` directly, bypassing `tools/hw-cargo`, thirteen times. Scope a test run to the crate you are changing (`sh tools/hw-cargo test -p <crate> --manifest-path engine/Cargo.toml`) while iterating. Widen it to `--workspace` mid-build only when the change touches something another crate depends on, such as a public type or a shared crate. Otherwise leave the workspace-wide run to the step `hw-build.md` names before the pull request opens.
- **The parent's own conversation is the largest single cost in a long run, and it is paid on every turn whether or not that turn does anything.** It never compacts and every prior turn is resent, so its cost grows with turn count times context size, not with the work done. Run `20260920-2058` measured its parent context grow from 62K to 721K tokens over 424 turns, averaging 409K; 126 of its 239 substantive turns were pure "still mid-flight, holding, no change" checks on a background agent, at an average context of 462K tokens each, for 58M cache-read tokens spent saying nothing changed. Those turns bought nothing. The parent's cache lives an hour, so a check keeps nothing warm that the next report would not find warm, and it learns nothing that the report would not bring. With agents in flight, end the turn and let the next report wake you. Never check on a timer, and never check more often as the run grows, because a check late in a long run costs many times what the same check cost at the start.
- **A report is the fixed block and nothing before it.** Every stage writes its narrative to `<scratch>/<stage>-report.md` by shell redirect and returns the block its definition names; the parent opens the file only when ruling. Forty of forty-one reports in one run ran two to four times the 400-token line, and the parent re-read every one on every later turn.
- **Backgrounding a job is half a decision; the other half is how you wait for it.** Decide both in the same breath, and end every wait you started before you exit — the last bounded call in a chain included, once the condition it names is met.
- **Redirect a build or a check to files and read the tail**, stdout and stderr to separate files. `sh tools/cap-run <command...>` does this in one call for a command that merges the two safely: it prints only the head, the tail, the omitted-line count, the exit status and the log's path, and keeps the whole run on disk. Do not reach for it on an invariant test that depends on reading stdout and stderr apart.
- **Ask an API for the field, never the record.** `gh api ... --jq .body` is the same fact at a fraction of `gh issue view`.
- **Never read a whole specification part.** `headwater explain` first, then `Read` with an offset and a limit.
- **Do not run the same command twice**, and count your repeats rather than trusting that you would notice.
- **Prefer `Edit` to `Write` on a file that exists**, and compose a long prompt or note in a file rather than in a shell argument.
- **Correct an environment claim the moment you disprove it**, in the place it was written.
