Run `$ARGUMENTS` iterations (default 20) of the Headwater build order, four Opus 5 subagents per iteration, **sequentially**. Merge between each, so iteration N+1 branches from N's merge and reads a board N already changed. Parallel runs do not stack; they collide.

**`--parallel N` is the one way to ask for anything else, and its absence means sequential.** Read the arguments for it, take N as the batch size, and follow *Running more than one iteration at a time* below. Without the flag, run the sequential shape this paragraph describes and do not offer the other one in the middle of a run. The flag is also the opt-in that `Workflow` requires: a run that carries it has been asked for multi-agent orchestration in the user's own words, and a run that does not has not been.

You are the parent. The subagents do the volume. Your job is judgment: what to merge, what a stale premise means, which of the agent's surprises is a lesson and which is noise. Almost everything you control sits in two places — **what you put in the next prompt, and what you refuse to take on trust.**

## The value rule

This is the canonical statement. Every other part of this file cites it rather than restating it, and so do `.claude/commands/next.md` and `.claude/agents/headwater-product-owner.md`.

**Before any work starts, name the reader who is not this repository.** If the only party better off is Headwater's own corpus, the work is not eligible for an iteration, and it is not eligible for the issue tracker either — see *Self-audit findings go to the register, not the tracker* below. Pick something else.

The rule exists because this command is an issue generator by construction. Part 1 tells the agent to file a tracker for everything it scopes out, part 4 hands it the open findings, part 6 hands it pre-work, and part 7 tells it to harvest its own report. All four are right and all four push in one direction. Nothing in the selection rules ever pushed back, and on 2026-08-15 the board took 45 new issues and closed 16 — 23 of them unplanned findings from running the engine over this repository. Part 3 already calls a register with an inflow and no sink a finding when it meets one anywhere else. This is that register.

A first version of this rule labeled such work `self-audit` and left it open on the tracker, on the theory that a defect nobody outside this repository can reach is a defect that costs nothing to hold. Measured over the eleven days that followed, that theory was half right: the work the label kept out of an iteration's hands did close fast (12-hour median), but the label itself never did — 24 filed, 3 ever closed, and every day from 08-16 to 08-26 still net-positive on the board as a whole. `self-audit` was a selection filter, not a sink, and calling it one was the error. The fix below gives it an actual sink.

**Self-audit findings go to the register, not the tracker.** A finding with no reader outside this repository is not filed as a GitHub issue at all. Scaffold it directly as an entry in [13 — Open obligations](docs/spec/13-open-obligations.md): `headwater new obligation_record --title "<the finding, stated as a debt>" --facet waiting_on=adopter`, fill Context, Obligation and Discharge from what you found, and add it under spec 13's *What the engine found about itself* heading. `adopter-blocking` still means what it did — work an outside adopter cannot proceed without — and it is still a GitHub issue, sorting above everything in the selection rules below. The distinction that mattered was never open-versus-closed; it was tracker-versus-register, and only one of those two has ever had a working sink.

## Keep going

**Do not stop between iterations.** The most common failure of this command is a parent that merges, writes a paragraph about what happened, and waits. Nobody asked for a status report. When an iteration merges, pick the next issue and launch the next agent **in the same turn**. Report when the run ends, when something needs a human ruling, or when the user asks.

Long stretches with no user message are normal and expected. The run is the task; a merged pull request is not a stopping point, it is the middle.

## The ledger

Keep a running ledger at `~/.claude/headwater-build-order-ledger.md`, **on disk, not in your context**. Twenty iterations will compact you at least once, and everything that makes this compound lives in the ledger. Read it at the top of every iteration and append at the bottom. Five sections:

- **Lessons.** What an iteration learned that the next should not rediscover.
- **Open findings.** Entries filed in [13 — Open obligations](docs/spec/13-open-obligations.md) — which is now where every self-audit finding lands — issues you opened for work with a reader outside this repository, and any defect you are handing forward.
- **Decisions needing an owner.** What you merged but would not merge again without a human ruling. Write it when it happens — the reason is legible then and paraphrased later.
- **Milestone status.** Which milestones closed, whose bar you verified, what the next one assumes.
- **Log.** One line per iteration: issue, pull request, merge commit, verdict, **what your own verification proved** rather than what the agent claimed, and **the net issue delta — opened minus closed**. Self-audit findings no longer move this number at all, because they no longer touch the tracker; count them separately, as entries added to spec 13. A run that nets positive on the issue delta for three iterations is a run building faster than it is deciding, and the delta is the only place that is visible while it is happening rather than in a review a week later.

**The ledger has a sink, and it is not optional.** Only Lessons has ever had a consolidation rule, so the other four sections grew without bound: by 2026-08-24 this file was **713 KB across 3,155 lines, about 100 KB per run, and nothing had ever been removed in eleven runs**. Every iteration pays that in context before it does anything. **Before each run, compact the whole file, not just Lessons** — retire an Open finding whose issue has closed, reduce an escalation to a pointer once the corpus records it, and compress the previous run's narrative into its Log rows, which this section already specifies as *one line per iteration* and which had been running a median of 1,577 bytes each.

**Harvest before you prune, because the narrative holds lessons the curated list does not.** A consolidation that only merges will drop them: the 2026-08-24 pass recovered five durable lessons that an earlier consolidation had lost, and **one of them was the lesson the very next iteration then reproduced** — *an issue that prescribes a remedy hands the agent a conclusion, and an agent that implements it cannot find the error* — dropped that morning and walked into within hours, with the parent's prompt substituted for the issue.

**On disk is defeated by writing it through a shell argument.** The point of the ledger is that it costs context only when you read it, and run 22 spent **31,568 tokens and 2.8M token-reads** putting it there — 40 `cat >>` calls, the largest a single 1,691-token heredoc — because a `Bash` input is context as permanent as any result. Write it with `Write` or `Edit`, or hand the append to the write-back phase, and keep the composing out of your own turns.

**Write the consolidated Lessons list back into the ledger, not into `$CLAUDE_JOB_DIR/tmp`.** A job directory is deleted with its job. The 2026-08-24 curated list survived only because somebody copied it out of a finished run's scratch space before it went, and it was by then better than the ledger's own copy. Everything a compaction removes goes to `~/.claude/headwater-ledger-archive/`, so the prune is reversible and can be argued with.

## What an iteration costs, and the shape that follows

**Measure the transcript by message, not by line.** One API response is written to the session log as several lines, one per content block, and every one of those lines carries a copy of the same usage record. Counting per line inflates turns and dollars by about 2.3 times, and it inflates them unevenly, because a response with four tool calls is copied more often than one with a single call. Group by `message.id` and take one usage record per identifier. The parent of the run below reads as 712 turns and $156 per line, and as 304 turns and $67 per message. Every figure in this section is measured the second way, and the figures it carried before were measured the first way.

Measured across 80 single-agent iterations: **77% of an iteration's cost is cache reads**, which is the accumulated context re-read on every turn. Output is 12% and cache writes are 11%. The median iteration runs 170 turns, peaks at 285k of context, and re-reads 32M tokens getting there. Nothing else you tune moves the number as much as what enters that context and how early it arrives.

The unit to think in is **carry**: a tool result costs its own size times the number of turns that follow it. Seven thousand tokens read at turn 20 of a 170-turn agent carry 1.05M token-reads; the same seven thousand read at turn 150 carry 140k. Position is worth as much as size, which is why the cheap-looking calls dominate. **Bash results are 68% of all carry and file reads 29%**, because an iteration makes 142 bash calls against eleven reads, and each 400-token result then rides every remaining turn.

**Hand the iteration to four agents rather than one.** The phases need disjoint context. Adjudication reads the board and the specification to settle whether the issue's premise still holds. Construction reads the code and runs the suite. Verification resets a worktree to the branch and attacks it. Write-back reads the diff and the board. In one context the specification prose sits underneath two hundred turns of `cargo test` output, and that output sits underneath the write-back, and none of it is ever dropped. As four agents passing a written note, each starts near 25k instead of inheriting 285k, and none of the four is you.

|  | Turns | Peak context | Cache read | Cost |
|---|---|---|---|---|
| One agent, median of 80 | 170 | 286k | 32.1M | $21 |
| Phase one, adjudication, median of 7 | 37 | 116k | 2.3M | $3 |
| Phase two, construction, median of 8 | 196 | 211k | 28.4M | $17 |

**The split buys peak context, and it does not buy dollars.** Adjudication at $3 and construction at $17 come to $20 against $21 for the whole of the old single-agent shape: a **4% saving**, measured over a complete ten-hour run that merged seven pull requests. The 30% this table claimed before was taken from the first two iterations of a run that was stopped, and early iterations are the easy ones. Construction grows back to 196 turns against the old shape's 170, because the work did not shrink when it moved.

What did change is worth having on its own. **Peak context per agent falls from 286k to 211k**, and an agent whose window fills reasons worse for every turn after it. Adjudication at 116k and $3 is cheap outright, because settling whether a premise still holds never needs the test output. Take the split for those two things and do not expect a bill to fall.

**Run 22 measured the shape with verification split out, and the split is working.** Parent 189 turns and 71.1M cache reads; 39 subagents 4,238 turns and 798.7M; **the parent is 9% of the run**, against the 27% the paragraph below recorded before verification moved out. What did not move is the growth: the parent climbed **65k to 687k with no compaction in under three hours**, past the 615k below, and its last 84 turns cost about twice its first 84 for the same work. Cache reads were **99% of every token billed**, across the run as a whole.

**You are now the expensive context.** In that same run the parent peaked at **615k and never compacted** — it climbed from 55k on its first turn to 615k on its last with no reset anywhere in ten hours, and it was 27% of the run. Its last 152 turns cost $43 against $24 for its first 152: the same work at nearly twice the price, because the context each turn re-reads had doubled. Every rule in this section applies to you with more force than to an iteration, because an iteration ends and you do not.

**Launch the run with `--tools`, because a schema you never call is read on every turn.** The built-in tool definitions are part of every request. Run 22's parent carried **28,987 tokens of them and never called ten of the fourteen**, which is 25,610 tokens re-read on all 189 turns, or 4.8M token-reads, for tools it had no use for. `Artifact` alone is 14,882 tokens — over half the budget — in a run that publishes no page. Measured on 2026-09-07: `claude --tools "Bash,Read"` brings the built-in total to **1,570 tokens**, so the flag does remove the definition rather than merely refusing the call. Name the union of what the parent and its phases use — `Bash,Read,Write,Edit,Glob,Grep,Agent,SendMessage,ListAgents,ToolSearch,Skill,Monitor` — and check it against what the last run actually called before you trim further, because a phase that needs a tool the flag withheld cannot ask for it. Nothing needs doing about the MCP servers: they are deferred already and cost nothing until a `ToolSearch` names one.

**The phase you kept is verification.** 101 of the parent's 304 turns in that run, and 36% of its cost, went on building and inspecting in worktrees the parent made for itself — one per issue, `wt-base` and six more — with 29 `cargo` invocations among them. Write-back, the phase this section did split out, was three calls. So the work actually sitting in your context is *Between iterations, before merging*, and that section now says which half of it to hand out.

**The saving is only real if you do not spend it waiting.** See the rule below, which the first run of this shape cost $26 to learn — more than the whole of a construction phase.

**The handoff is a file, not a context.** Phase one writes the adjudication into the iteration's scratch directory: the premise verdict, what it will build, and the decisive fixture. Phase two writes what it built, what it ran, and what the numbers were. Phase three writes the verdict: which attacks fired, which did not, and what it could not check. Phase four reads those three notes and the diff. A phase that needs something an earlier phase saw and did not write down is telling you the note is too thin — thicken the note rather than merging the phases back together.

**The file is for the phase that reads it next. The report comes back to you on its own.** A phase agent's final message reaches you when it completes, so the verdict, the number and the surprise belong there, and none of it needs asking for. Write the file for the next phase; read the return value for yourself.

**Cap the report, because the note is free and the report is not.** A phase's note on disk costs you nothing until you read it. Its returned message is injected into your context and stays there for the rest of the run. In run 22 the returned reports were **your single largest input class at 113.7k tokens** — a median of 1,475 each and a largest of 5,972 — and three agents notified two or three times, re-injecting the whole report on each. **Ask for under 400 tokens back**: the verdict, the numbers that moved, and the surprise. Everything else goes in the note, where the phase that needs it reads it and you do not.

**Wait by blocking, and never by polling.** A phase agent runs in the background and tells you when it finishes, so between launching it and its report you have nothing to do. Do not fill that with checks. The first run of this shape made 232 identical `git log origin/main..<branch>` calls in twelve minutes, a median of three seconds apart, and narrated *"I'm burning turns polling"* while it went on polling — **236 of that parent's 405 turns and $26 of its $44**. Read those two numbers together: a poll is a cheap-looking turn, so counting the transcript by line hid more than half of it, and the first write-up of this incident called it a third of the turns when it was nearly three fifths. Every check re-reads your whole context, so a poll is the most expensive way available to do nothing. **Wait for the completion notification.** Where you must wait on a file a phase writes, spend one blocking call — `until [ -f <path> ]; do sleep 30; done` — rather than a check per turn, and never a sleep shorter than thirty seconds. **Whether a pull request is mergeable is the same wait, and it is the one this rule kept missing**, because the rule named a file on disk and `mergeable` is a field GitHub computes after you ask: spend `until [ "$(gh pr view <N> --json mergeable -q .mergeable)" != "UNKNOWN" ]; do sleep 30; done` rather than one `gh pr view` per turn. In the run measured below, 63 of the 76 `gh pr view` and `gh pr list` calls were bare one-shots and only 13 sat inside a loop. Across the five parent sessions before this shape existed, not one repeated a single command more than twenty times; the first session under it repeated one 232 times. The failure is available to you and it does not announce itself, so count your repeats rather than trusting that you would notice.

**Counting repeats does not catch the version of this that is spread thin, so count the class as well.** The 232-call incident was one command hammered in twelve minutes and it is visible from any angle. The same parent later spent 76 calls asking after `mergeable` across **43 different pull requests** — about one and a half calls each, no single shape repeated more than 40 times, nothing that looks like a loop from inside the turn taking it. It cost **77 turns and 21.3M cache reads, 10.3% of that parent's entire 207M**, to carry results totalling 25 KB. Group your shell calls by what they are for rather than by their text, and read the total: a habit priced per turn is expensive at any repeat count, because the turn re-reads your context and the answer is one line.

**The coordination has outgrown the waiting.** Three phases and two handoffs was the line this paragraph drew, past which the sequence belongs in a script rather than in your turns. Verification makes it four phases and three handoffs, so the shape is now over that line by its own rule. `Workflow` is that script: it runs the phases in a fixed order, hands you each phase's return value directly, keeps every phase's tool output out of your context, and never puts you in a position to wait at all — which retires the polling failure above by construction rather than by a rule a parent has to keep remembering for ten hours. It costs a decision from the human to start, so **raise it at the top of a run rather than in the middle of one**, with the measured numbers from this section as the case. Judgment between iterations — what to merge, what a stale premise means — stays with you either way.

## Running more than one iteration at a time

**This is a different question from the four-agent split above, and the two do not substitute.** That split divides *one* iteration into phases that need disjoint context. This divides the *run* into iterations that land in parallel. The line at the top of this file — *parallel runs do not stack, they collide* — was written about running the whole loop twice, and it stands. What follows is the narrower thing that works: several iterations building at once, one merge decision, still yours.

**What used to make this unsafe is fixed, and knowing which half is fixed matters.** [HW-DR-0049](../../docs/decisions/0049-a-corpus-wide-fold-is-derived-and-never-stored.md) rules that a recorded artifact holds one record per entity and derives every total. The census and the graph now merge correctly when two branches each add a document. What is *not* fixed is the artifact that keeps its fold, and the rule that record states is the one to carry into every parallel branch: **an artifact that stores a count over the whole corpus merges quietly and wrongly when the branch carrying it is behind `main`.** Nothing in a private repository on a free plan refuses that merge. Read the record rather than a summary of it here.

**So the one instruction every parallel worker gets, in its prompt, is this.** Before you ask for a merge, rebase onto `main`, **rebuild the engine**, then run `headwater generate` and re-bless the recorded fixtures, and read that diff. A branch that skips it can be green on its own tip and still turn `main` red, and no reviewer of that branch could have seen it.

**The rebuild between the rebase and the generate is not optional, and leaving it out fails silently.** `headwater generate` writes committed artifacts, so a binary built before the rebase writes what the previous engine produced. `headwater check --strict` then exits 0, because the same stale binary wrote the artifact and checked it, which is a claim verified by the thing that made it. One rebase onto a merged change that moved the navigation stripped all ten `Index:` entries out of `.headwater/nav.yml`, and every local check passed it. CI caught it, through `mkdocs build --strict` and the test that rebuilds the artifact rather than reading it. Treat a peer's merged change to generation as invalidating your binary rather than as a conflict risk.

**Claim through the board, never through a coordinator.** A worker takes its issue by assigning it to itself and moving it to In Progress. That claim is atomic, it is durable, it survives a worker that dies, and you can read the whole state without asking anybody. A coordinator holding N workers' states in its own context is the polling failure of the section above with N times the input, and every message it routes re-reads its whole context. Scaling up or down is then starting or stopping a worker rather than correcting a scheduler written in prose.

**`Workflow` is what runs the workers, and the shape is one call.** The paragraph above about coordination outgrowing the waiting makes the case, and it makes it for the phases of one iteration. It carries to several iterations without change, because `pipeline(issues, adjudicate, construct, verify, write_back)` is that shape exactly: each issue moves through all four stages independently, with no barrier between them, so issue A can be in verification while issue B is still being adjudicated. Wall clock is the slowest single chain rather than the sum of the slowest stage in each round. Do not reach for `parallel()` between the stages. A barrier there would hold every finished construction until the slowest adjudication returned, which is the cost this whole section exists to avoid.

**Watch the spread between the first and the last completion in a batch, not the batch's wall clock.** Subagent runtime has a long tail: in the measured run the median was 13.5 minutes, the ninetieth percentile 46, and the longest 91. Across the batches of three agents or more, 9.3 hours separated the first completion from the last. That is what a barrier costs when it is there by accident rather than by `parallel()`. A batch that advances only once its slowest member returns has the barrier this section tells you not to write, whatever the code says. Read the spread every batch, and move the finished items on rather than holding them for the batch.

**Give construction `isolation: 'worktree'`, and nothing else.** Two agents building two issues write files at the same time, which is the one case the flag is for. It costs setup and disk for each agent, so adjudication, verification and write-back do not take it.

**A workflow cannot merge, and that is the constraint that shapes the run rather than a limitation to work around.** You are not in the loop while it runs, so nothing inside it can make the decision that this file says never leaves you. So a run produces *N branches ready for review*, and you then merge them one at a time. Each one rebases onto the merge before it, which is where the rebase that [HW-DR-0049](../../docs/decisions/0049-a-corpus-wide-fold-is-derived-and-never-stored.md) asks for actually happens, and it happens once per branch rather than once per run. That serial tail is not waste. It is the merge queue this repository cannot buy, run by you. Run that queue through *The integrator slot* below rather than in your own turns: the ruling is yours and the mechanics are not.

**So the loop is: fan out, drain, merge, fan out again.** One workflow per batch, and you read what came back before choosing the next batch. That keeps the property the top of this file cares about — an iteration reading a board that the one before it changed — at the grain of a batch rather than of a single issue.

**Four stages times N issues is 4N agents, and this session's guideline is 15.** Three issues is twelve and fits. Four is sixteen and does not, so raise the guideline under *Dynamic workflow size* in `/config` before asking for four, rather than discovering the ceiling in the middle of a run. Concurrency has a second and lower ceiling that no setting moves: a workflow runs at most `min(16, CPUs - 2)` agents at once, and the rest queue.

**A stage that throws drops its own issue and leaves the others running.** That item becomes `null` and skips its remaining stages. So one bad issue costs one branch rather than the batch, and `.filter(Boolean)` on what comes back is what tells you which ones survived. Say which ones did not, rather than reporting the survivors as the batch.

**It needs the human to start it, every time.** `Workflow` is opt-in per run and this file cannot grant that. Raise it at the top of a run with the numbers from the cost section as the case, never in the middle of one.

**Cap it at two or three and raise it on a measurement.** The merge decision never leaves you, and verification was 36% of the parent's cost in the last measured run. Adding workers multiplies the part that is already the constraint rather than the part that is cheap. Watch one number: worker idle time against wall clock from branch-ready to merged. If workers wait on you or on the runner, another worker buys nothing.

**Width is measured, and wider is not better.** One run raised the width from five to eight in the middle of itself. Mean concurrency fell from 4.00 to 3.22, and the share of the window with an idle fleet rose from none to 32.1%. Five was the only setting that kept the fleet busy for the whole of its window. Widening multiplies the work that funnels back through the parent rather than the work that runs beside it, so it buys nothing until the integrator slot is draining and the pull request polling has moved out to the jobs. Raise the width after those two moves and on that measurement, rather than on a guess.

**One self-hosted runner serves this repository and it takes one job at a time.** Three or four workers pushing turns CI into a queue. `.github/workflows/ci.yml` cancels a superseded run on a pull request so that a dead commit does not hold the runner, and that is the whole of what configuration can do here. More parallelism than the runner can absorb shows up as idle workers, which is the number above.

**At the widths measured so far the runner has not been the constraint, so do not spend a run tuning it.** In the measured run 44 of 45 pull requests merged, at a median of 40 minutes from opening to merge, and the queue above never showed up as idle workers. The constraint was upstream of all of it, in the parent's own turns, which is what *The integrator slot* below exists for. Re-measure before believing either paragraph: the runner becomes the constraint at some width, and nothing here has found it yet.

**Prefer issues that do not collide.** Engine-only work that adds no document under `docs/` touches none of the recorded artifacts. Two issues in different milestones rarely edit one register. An `adopter-blocking` issue is worth your own attention rather than a pool slot, and there are few of them.

## Each iteration's prompt

Build it fresh. It must contain all seven parts.

### 1. The procedure the agent follows

Subagents do not get slash commands, so paste this in full. An agent told to "run /next" invents its own idea of what that means.

**This is the whole iteration, and it goes out in four pieces.** The adjudication agent gets everything through *Check the issue against reality* and writes its verdict to the scratch directory. The construction agent gets *Do the work*, the amendments, and that verdict. The verification agent gets the branch, the checklist under *Between iterations*, and the attacks you chose. The write-back agent gets *Write back* and *Report*, the notes, and the diff. Parts 2 through 7 below are not addressed to all four: every phase gets part 2, adjudication gets 4 and 5, construction gets 3, 5, 6 and 7, verification gets 5 and 7, and write-back gets 5.

**The open board is adjudication's input, so read it there and never here.** Checking an issue against reality needs the board, and the board is large: one parent spent 16 `gh issue list` calls on **51.8 KB, about 12.9k tokens**, and the three largest were whole-board dumps of 8 to 14 KB from `--state open --limit 200`. A dump you read once to pick an issue is then re-read on every turn for the rest of the run. Ask adjudication for the board it needs and require back the issue and the verdict, not the listing. What you keep is the number you are ruling on.

> **Work exactly one iteration of the Headwater build order** (org project "Headwater build order", `headwater-ai/headwater`), then stop.
>
> **Read the board first**, because it moves under you. **Take the population from the issue list, never from the project board** — `gh issue list --state open --limit 200 --json number,title,labels,milestone`. On 2026-08-24 the project held 44 of 74 open issues and was missing **every** `adopter-blocking` one, because nothing adds a newly filed issue to it ([#280](https://github.com/headwater-ai/headwater/issues/280)); an agent reading `gh project item-list 1 --owner headwater-ai --format json` as the population cannot see the top of the selection order. Use the project for the status of what it holds. Then read the milestone epic and any issue the candidate says it depends on. Read the milestone list itself as well — `gh api "repos/headwater-ai/headwater/milestones?state=all&per_page=100"` — because a milestone finished and left open makes the lowest-with-open-issues rule read the wrong one.
>
> **The issue is already picked for you** (see below). For the record, the selection rules are: **first, the issue must name a reader who is not this repository — a legacy issue still labeled `self-audit` is not eligible (self-audit findings are no longer filed as issues at all — see *Self-audit findings go to the register, not the tracker*, above), and one labeled `adopter-blocking` sorts above everything else**; then anything already In Progress and unfinished; then anything labeled `correctness-root`, because [spec 12](docs/spec/12-check-layer.md) says every check trusts it silently; then the item that unblocks the most others; otherwise the lowest issue number in the milestone.
>
> **The last rule has a fallthrough, and it is not optional.** When the lowest milestone with open issues has no eligible candidate left — everything in it is `self-audit`, blocked or already taken — do not skip to the next milestone first. Look at the eligible issues carrying **no milestone at all**, because they are invisible to every rule above and can sit there indefinitely. Take the one whose reader is most immediate, and say in the pull request which milestone's bar you believe it answers to. On 2026-08-20 six eligible issues sat unmilestoned and unreachable, and one of them was the command an outside contributor is told to run.
>
> Every rule after the first is an internal ordering, and an internal ordering cannot tell you whether the work was worth doing. That is what the first rule is for.
>
> **Check the issue against reality before building.** The body was written at a point in time. Confirm its premise still holds against `docs/spec/`, [9 — The decision register](docs/spec/09-decisions.md) and [13 — Open obligations](docs/spec/13-open-obligations.md). If it does not, say what changed and do not implement a stale ask. **Running inside `/next-run`**, adjudicate it yourself and say plainly in the pull request what you decided — do not halt, because the parent verifies the result and can redirect. **Running solo under `/next`**, there is no parent to catch a wrong guess: say what changed and ask rather than guess.
>
> **Where the change would extend an interface contract, a decision's stated clause, or an existing `tests/*.rs` case table, extend that first.** Add the new case against the contract as stated, run the suite, and confirm the new case fails for the change's own reason — not a compile error, not an unrelated panic. Only then write the implementation it targets. Where nothing like that exists yet, the shape is still open: a test committed to a guess costs more than one written once the design is settled, so build normally and add fixtures alongside the code.
>
> **Do the work.** Follow `CLAUDE.md`. Branch, small commits, a pull request. The bar is the issue's "Done when", not a reading of the title.
>
> **Write back. This is the part that compounds and it is not optional.** Comment on the issue wherever it was wrong — interfaces that came out different, assumptions that failed, cost that surprised you. Edit the downstream issue bodies this work invalidated, saying in the edit what changed and why. Route any finding that contradicts or sharpens a closed decision to spec 13; spec 9 is a register of settled decisions and accepts no new questions. If the work supplied or killed an instrument for an unmeasured claim, move the `discharges:Qn` label and the matching spec 13 entry. If the milestone order is now wrong, say so with the reason — do not re-plan in silence.
>
> **Report four lines**: what shipped, the pull request, what the next iteration should pick and why, and **what you learned that is written down nowhere yet**. If that last line is empty, say so — it rarely is, and an empty answer usually means the write-back was rushed.
>
> Do not start a second issue.

Add these amendments every time:

- **An honest split is a success condition, not a failure to hide.** If the issue is more than lands in one pull request, split it on the board, take the first sound piece, file the remainder, and return `Refs #N`. In the last run five of nine iterations did this and every one was right.
- **State each write-back as you land it and then verify it took.** An agent once wrote "removing the label from this issue" in an otherwise flawless adjudication and the label was still attached.
- **Every "not made here" needs a record, and every record names its reader.** Scoping something out is often right; leaving it unrecorded never is. A finding whose only beneficiary is this repository's own corpus is not a GitHub issue at all — scaffold it as an entry in [13 — Open obligations](docs/spec/13-open-obligations.md) (see *Self-audit findings go to the register, not the tracker*, above), and it is not work the next iteration may pick. Keep the honesty and drop the automatic promotion to work.
- **Cap the self-audit intake per iteration, at three, same as before** — past that, one obligation-register entry that lists the rest, rather than one apiece. The register carries its own cost: it is hand-maintained, and its own count has gone stale by hand before ([HW-OBL-0142](../../docs/obligations/0142-the-obligation-register-states-its-own-size-by-hand-and-it-went-stale-three-times-in-two-days.md)). A single iteration once put 23 unplanned findings on the issue board, and no reader outside this repository was waiting on any of them; the register is a better home than the tracker was, and it is still not a place to be careless with volume.
- **Every issue you file or edit opens with an `## ELI5` section.** `.github/ISSUE_TEMPLATE/issue.md` is the shape and the only copy of it; `gh` does not apply it, so read it and follow it. Two to five sentences of plain language before the dense lede, for a reader who has never opened this repository. An issue whose ELI5 cannot be written without the jargon is usually an issue that is not yet understood, and that is worth saying in the body rather than papering over.

### 2. The environment traps

Carry the whole list forward — it is cheap to paste and each entry cost somebody an hour.

- `gh issue view` and `gh pr edit` fail with a `projectCards` GraphQL deprecation. Use `gh api repos/headwater-ai/headwater/issues/<N> --jq .body`, and patch bodies with `gh api -X PATCH repos/headwater-ai/headwater/{pulls,issues}/<N> -F body=@file.md`. Read the comments too — corrections live there.
- Worktree isolation refuses heredocs and compound shell. Write scripts to files and run them.
- **Give the agent its own scratch directory**, `$CLAUDE_JOB_DIR/tmp/issue-<N>/`, and tell it your own instruments live in `$CLAUDE_JOB_DIR/tmp/parent-only/` and are off limits. An agent once wrote its checking script onto the exact path holding yours, and your "independent" re-derivation then ran the agent's code against the agent's work with nothing to tell you. **The rule is not holding.** Iteration agents opened `parent-only/lessons-seed.md` and `parent-only/seed.md` 24 times across 80 iterations. Saying it once in the prompt has not been enough; read the transcript for the path.
- `Write` is blocked in the shared checkout and `EnterWorktree` is refused from a subagent. Tell it to create one by hand: `git worktree add .claude/worktrees/<name> -b <branch> origin/main`, staging files through its own tmp subdirectory, leaving the shared checkout untouched on `main`, and removing the worktree at the end or saying it is still there.
- `git push -u origin <branch>`, never a bare `git push` — `push.default` is `matching` on this machine, so a bare push also tries to push a stale local `main`. Branch from `origin/main` after a fetch.
- The pinned container is `rust:1.90-slim` while CI runs current stable, so clippy differs and `-D warnings` promotes new lints. Run it with `--user` and a container-internal `CARGO_TARGET_DIR`. `--user` and `rustup component add` cannot both work there, because rustup needs a writable `RUSTUP_HOME`, so a formatter fix is applied by hand. **Capture each step's exit status separately** and check CI rather than trusting a local green run.
- **Never pipe the gate.** `<gate> | <filter> && <next>` reports the filter's exit status, so a failure passes silently.
- **Never merge stderr into stdout on an invariant test.** `headwater check` prints a run statistic to stderr and the artifact to stdout; `2>&1` makes a correct invariant look broken. An agent once wrote "the cache invariant is literally false" into durable memory on the strength of one.
- **A test of the engine must re-resolve the lock.** `headwater check` reads `.headwater/taxonomy.lock` and never the package sources. Run `headwater taxonomy resolve` between editing `packages/` and checking — **and mind the order**: resolving *before* publishing moves the lock with the source, so both sides match again and a comparison you meant to fail passes. That one is mine, from testing `taxonomy diff`.
- Build with `cargo build --release -p headwater-cli --manifest-path engine/Cargo.toml --locked`. **The full suite now outlasts a ten-minute timeout after a widely-depended-on crate changes** — redirect to a file and run it in the background rather than inline.
- **More build threads is not the lever, and the reason is in the profile rather than in the flag.** Cargo already runs at one job per core and nothing here caps it, so there is no `-j` to raise. `[profile.release]` sets `lto = true` and `codegen-units = 1`, and both of those phases run in one thread by construction, so the part of the build that costs the most is the part `-j` cannot divide. The host has 8 cores and was measured at a load average of 44 during a run with several sessions building at once, which means another thread takes time from a neighbor rather than finding an idle core. Raising parallelism here buys nothing and can cost.
- **The lever is the profile, and it was measured on this host inside a run.** The same workspace built in **53.8 seconds** under `cargo build --profile dev-release` and in **151, 233, 320 and 383 seconds** under `--release` on four occasions the same day. `[profile.dev-release]` keeps `opt-level = 3` and drops only `lto` and the single codegen unit, which is exactly the serial part above. Use it whenever you want to run the real CLI a few times, and never for a release artifact or for a performance claim.
- **What stops that being free is where the gate looks.** `.githooks/pre-commit` and `.claude/hooks/lib.sh` both name `engine/target/release/headwater` as a literal path, and `--profile dev-release` writes to `engine/target/dev-release/`, so a `dev-release` build leaves the commit gate reading whatever old binary sits on the release path. That is the stale-engine failure this repository already knows: the gate does not fail open, it fails confidently. Do not shortcut it by copying the binary across either — that puts a binary on the release path that cargo's own fingerprint for the release profile did not produce, and nothing here has measured what the next `--release` build then decides to skip. Build `--release` when the gate has to run, and `dev-release` when it does not.
- **`cargo` runs a target's cases as threads of one process, so `std::process::id()` is not a unique key per test.** A temp-dir helper keyed on the pid alone breaks when a second `#[test]` joins its file, and the symptom is `NotFound` out of `std::fs::copy`, which reads as a missing fixture rather than a race.
- **Commit and push in small steps.** A transport error or an API limit costs everything unbanked, and only pushed commits survive an agent death.
- `git config core.hooksPath .githooks` in the worktree. A `Stop` hook runs `.githooks/pre-commit` and exits 2 on failure; dormant while `--strict` exits 0.
- A rust-analyzer LSP is available. **Never navigate from its `documentSymbol` line numbers** — they point at an item's first doc-comment line, not its signature, and the gap runs to sixteen lines in this codebase. `findReferences` at the wrong line returns "No references found", which is indistinguishable from a true negative. `grep -n 'fn <name>'` first.

**Token discipline is the same list read for cost.** Each entry below was measured across 80 iterations, or on run 22, and each is worth more than it looks, because a result rides every turn that follows it. **Every phase gets this list, and the first entry is the one that has cost the most.** The rule below about waiting lived for four runs in the parent-facing half of this file, where a subagent never saw it, and run 22 spent a fifth of itself proving that a rule an agent cannot read is a rule nobody keeps.

- **Redirect a build or a check to files and read the tail.** `cargo test` ran 447 times and `headwater check` 209, for a quarter of a million tokens that never leave the context once they arrive. Send stdout and stderr to *separate* files — the trap above about merging them still holds — as `cargo test ... > $TMP/test.out 2> $TMP/test.err`, then read `tail -5 $TMP/test.out` as its own call. Two calls rather than one compound command, because worktree isolation refuses the compound form anyway.
- **Ask an API for the field rather than the record.** `gh issue view` cost 79k tokens over 138 calls. `gh api repos/headwater-ai/headwater/issues/<N> --jq .body` is the same fact for a fraction of it, and the traps above already require that form for an unrelated reason.
- **Never read a whole specification part.** `02-taxonomy-model.md` is 24k tokens and `07-distribution-and-federation.md` is 20k. Use `headwater explain`, or `Read` with an offset and a limit. File reads are 29% of carry and it concentrates in whole-file reads that land early and then ride the entire run.
- **Do not run the same command twice.** 693 exact-duplicate calls across 80 iterations, about eight an iteration. A repeat costs its output a second time and adds a turn, and turns are the multiplier on everything else in the context.
- **Wait by blocking, never by polling. This is the most expensive mistake available to you.** A status check costs a whole turn, and a turn re-reads your entire context, so a poll is the most expensive way there is to do nothing. Spend **one** call and let it block — `until [ -f $T/x.status ]; do sleep 30; done` — or use `Monitor` with an until-condition. **Never a sleep shorter than thirty seconds**, and never a bare re-check of a file you have already checked. Measured on run 22: one construction agent checked `bless.status` **85 times across a five-minute wait, at a three-second cadence**, `mutate.status` 63 times and CI 76 times, for **328 repeated calls out of 598**. That one agent burned 231.7M cache-read tokens, **29% of the whole run**, against a median agent of 72 turns. Across all 39 agents of that run, repeated commands cost **172M tokens, 21% of everything spent**. The agent that did it had `Monitor` loaded and had used it four times, so the tool was never what was missing.
- **Backgrounding a job is half a decision, and the other half is how you will wait for it.** This list tells you to redirect a long build to a file and run it in the background, and tells you never to detach one. Decide the wait in the same breath you launch the job. An agent handed the first half and not the second polls, every time, and the two entries sat three lines apart for four runs without anybody reading them together.
- **Count your repeats rather than trusting that you would notice.** The failure does not announce itself and it feels like diligence while you do it. The parent that first hit this wrote *"I'm burning turns polling"* into its own transcript and then went on polling for another two hundred calls.
- **Prefer `Edit` to `Write` on a file that already exists.** `Write` carries the whole new body in the request: 1,508 calls at an average of 1,024 tokens, which is 45% of all tool-input volume.
- **What you send costs more than what comes back.** This list is written about tool results, and in run 22's parent they were the smaller half: 52k tokens of results against **141k of tool inputs**, where the `Agent` prompts alone were 68.8k. A command you compose, a prompt you write and a heredoc you paste are all permanent context. Compose them somewhere else and pass a path.
- **Do not compose a long heredoc in your own turn.** Run 22 wrote its ledger through 40 `cat >>` calls totalling **31,568 tokens**, one of them 1,691 tokens in a single command. The ledger is specified below as living on disk rather than in your context, and writing it through a shell argument puts every word of it in both.

**Correct an environment claim the moment you disprove it.** An agent reported an invariant "literally false" and wrote it to memory; it had captured `2>&1` and read a stderr statistic as part of a stdout artifact. Left standing, that would have taught every later iteration to weaken the strongest test in the repository. If an agent's environment claim contradicts a recorded lesson, measure it yourself before it propagates — and if the agent wrote it somewhere durable, go and fix that too.

## Between iterations, before merging

**Run this in an agent; decide it yourself.** What follows is two jobs wearing one name. Choosing which attack is worth making is judgment, and it stays with you. Resetting a worktree, building it, running the suite, grepping the tree and reading a diff is execution, and it was 36% of the parent's cost in the last run, for output you read once and then carried for ten hours. Hand the execution out as its own phase, third of the four: give the agent the branch, the list below, and **the specific attacks you chose**, and require back a written verdict — what it ran, what the numbers were, which attacks fired, which did not, and every claim it could not check. Read the verdict. Do not read the build output.

Keep in your own turns only what you must see yourself: a diff you are ruling on, and a number you are re-deriving because the agent's contradicts yours. **The merge decision never leaves you**, and neither does the judgment below about what to attack, what a stale premise means, or what belongs in *Decisions needing an owner*. A verification agent that comes back saying everything passed has told you what it ran, not that the branch is sound — the rule about suspecting your own check first cuts both ways, and it now has a third party in it.

### The integrator slot

**The merge is two jobs wearing one name too, and only one of them is yours.** Ruling on what merges is judgment and it never leaves you. Running `gh pr merge`, fast-forwarding the one main checkout, rebuilding the one `engine/target`, regenerating and re-blessing is execution. In the last measured run it was 61% of the parent's serial shell time, and `cargo build` alone was 49% of it, at 67 minutes over 26 calls. Merging is the cheap half: 46 merges cost about eleven seconds each. It is the build behind the merge that holds the run.

**So drain it through an integrator slot of depth one.** Keep a queue of merge requests you have already ruled on, and drain it one at a time with **a fresh agent per merge**. Give that agent the pull request number, the branch and the ruling you made. Require back what it merged, what `main` is now, what the regenerate changed, and anything it could not complete. Read that. Do not read the build output.

**Fresh per merge, and never one long-lived integrator.** An agent held open across a run accumulates every merge it ever ran and begins compacting, which is the parent's own failure reproduced one level down. The measured run compacted five times, and its single largest gap of 82.8 minutes ended at one. A short-lived agent carries one merge and exits with it.

**Depth one is a mutex rather than a tuning constant.** Every merge is the same shape: merge the pull request, fetch, check out `main`, fast-forward, and often rebuild. Every one of them touches the same working directory, the same `engine/target` and the same `origin/main`, so two running per job would check out `main` in one checkout at the same time. The correctness argument is the stronger one. A post-merge regenerate run concurrently is the case [HW-DR-0049](../../docs/decisions/0049-a-corpus-wide-fold-is-derived-and-never-stored.md) covers, where two branches derive the same wrong total and merge clean at exit 0, and nothing in a private repository on a free plan refuses that merge.

**Do not make the build per-worktree to escape the serialization.** A fresh worktree has no engine, so the commit gate fails open and reports nothing at all. `sccache` bakes a dead worktree's path into a test binary, so a cargo failure quoting `.claude/worktrees/` is a cache hit rather than a defect. One warm target directory behind the slot beats several cold ones, which is the reason the slot is worth standing up rather than a cost it imposes.

**What stays with the job.** Reading a pull request for `mergeable` and `mergeStateStatus` belongs to the agent that owns that pull request. In the measured run it was 17 minutes of parent turns spent polling other agents' work, and wall clock is the cheap half of that price, which *Counting repeats does not catch the version of this that is spread thin* above prices in cache reads. Do not read either paragraph as a case for handing each poll to an agent, because an `Agent` call is itself a parent turn at the same context and carries a prompt on top: the call is already as small as it can be, and what is expensive is the parent being the one to make it. It belongs to whoever is already waiting on that pull request, which is the integrator draining the slot or the agent that opened it. Bookkeeping goes the same way: one file per job, collected at the end, rather than every worker appending to one shared notes file. Both moves cost nothing, and they are what stop the parent from being the place every job reports through.

**The number that says whether the slot is working is the share of the run with no agent in flight at all.** The run this was measured in dispatched 152 agents and held a mean of 3.03 in flight against a target of eight, with nothing running for 20.9% of the window: 3.4 hours across four windows, the largest of them 114 minutes, spent merging and building alone. If the fleet still goes quiet while you integrate, the slot is not draining and you are back in the loop it exists to take you out of.

**Verify independently and adversarially.** Reset a scratch worktree to the branch and run the suite, the linter and the CLI. That is necessary and nowhere near sufficient — it catches almost nothing the agent has not already caught. What actually finds things:

- **Make the new thing fail.** Break the corpus by hand and confirm the new rule fires with a message naming the offender. A check that fires on no input is indistinguishable from one that does not work. When a change reports *fewer* findings, attack that hardest.
- **Test a gate in three directions, not two.** A real drift must fail it; an ordinary edit elsewhere must not; and **a change to a source must make the derived artifact go stale**. Only the third separates a derived artifact from a snapshot somebody typed.
- **Choose the edits yourself.** Run the agent's own decisive scenario with *your* documents, not the ones its fixtures use. Twice this has found the test narrower than its name.
- **Attack a number that did not move.** Inject defects into the *new* material. It is the only way to tell "the new documents are clean" from "the new documents are on a shelf no rule reaches".
- **Check a new rule gained instances, not just existence**, and make the agent predict the number before running it.
- **Run the next component, not just the one that changed.** A correctness root's own suite cannot fail on a defect that lives one component downstream.
- **Regress the implementation to prove a new test can fail, with a different regression from the agent's.** This is how you learn that a fix is unheld: revert it and watch the whole suite stay green. **Note when a regression will not compile** — that is the strongest result available, because it means the wrong state is unrepresentable rather than merely tested for.
- **Report cache-hit counts, not just verdicts.** A byte-identity differential compares verdicts and cannot see a rule that has become permanently unkeyed. Read keyed and not-keyed before and after and check the delta is the arithmetic of what was added.
- **Re-derive one claimed number by hand**, with your own script, naming the denominator.
- **Validate artifacts with something that is not this system** — an external parser, a published schema, a stock validator.
- **Reproduce a performance claim in the build configuration the claim implies.** Debug and release differ by an order of magnitude.

**Ask the review questions.** Is the named value **injective** over the states that change the verdict — not "is the input named?" but "can two states that must differ produce one key?" Is there an **`Option` at a parse boundary** destroying the difference between "observed nothing" and "did not observe", where the wrong reading is always the one that returns green? Does an **empty arm have a location** — a row nobody wrote, or a column nobody declared? Does the **treatment arm prove the instrument** or only the subject?

**When your own check contradicts the agent, suspect your check first.** Across four runs I have been the one who was wrong more often than not. The most expensive was a denominator — see part 5. The rest, briefly, because each is live: deriving a GitHub anchor slug by the wrong rule (each space maps to one hyphen rather than collapsing runs, and `_` is kept); counting citations from a test fixture that is not corpus content; reading a token that survived `--fix` as a miss when the rule's table is a closed set that never contained it; reading a stale lock the engine deliberately never reads from source; resolving before publishing so both sides of a comparison moved together; and running a git-dependent fixture suite over a `git archive` export, where the commit-gate cases fail for want of a `.git` — a real `git worktree` of the same commit passes clean.

**If the agent was right, say so plainly, correct anything you already wrote down, and move on.** Two adjacent traps: a broken path and a broken fragment are different defects and a fragment checker sees only one, so check the path resolves before the anchor; and a deliberate fixture that is *meant* to dangle shows up in every sweep, so establish the baseline on `main` before reading the branch's number as a regression.

**Use Fable as a second opinion, judiciously.** `Agent` takes `model: fable`, which gets you a genuinely different model rather than another instance of the one that wrote the work and the one checking it. Opus verifying Opus shares blind spots, and the failure this whole command is built against — a confident, well-argued, plausible claim nobody re-derives — is exactly what a same-model reviewer is worst at catching. It has found a live defect in three of the last eight branches.

Spend it where a second reading changes what you do: a ruling you are about to merge; anything heading for *Decisions needing an owner*; a claim you cannot cheaply re-derive where the cost of being wrong is a milestone; the largest change of a run; and the escalation list at the end. Not on routine merges.

**Give it the repository, not only the artifact and the argument** — handed only an artifact a refuter can test coherence, and coherence-testing yields the cheapest hit available (*outcome right, reasoning wrong*), which is real and also the class to discount hardest. **Ask it to refute rather than review**, and tell it "I could not break this" is a respected answer, because a refuter who must produce something produces something. Then treat what comes back as a second opinion: **verify its checkable claims before acting on any of them** — it will be confidently wrong too, just in different places, and that asymmetry is the entire value.

**Know the limit of your own verification.** For forty-five iterations across three runs, merge-refusal never once fired, and the honest description was not "your job is what to merge" but "verification shapes what merges, and merging has been unconditional". **In the fourth run it fired twice** — both times as *send it back to the agent that wrote it*, not as a rejection, and both times the work came back better than the correction asked for. So the veto is real, but it is a resume rather than a bin. Two consequences still hold:

- **A run can rewrite a bar and then close against it.** This command licenses replacing an unmeetable bar with what is true, and licenses closing an epic whose bar you verified. Together they let a run set its own finish line. When you rewrite a Done-when and later close against the rewritten one, **say so in the closing comment and flag it for ratification**.
- **Your verification is iteration-grained and some defects only accumulate.** The worst finding of one run — that every agent-drafted document carried an acceptance stamp the drafting agent typed — was found because one issue happened to measure it. **Once a run, ask what would only be visible across all of it**, and measure it rather than recalling it.

## Policy, so nobody stops to ask

- **You adjudicate a stale premise; the agent does not halt.** Escalate to the human only when the redirect would change milestone order, or when a decision needs an owner rather than an answer.
- **If an issue is three pieces, say so and pick it anyway** — unless it will not land in one pull request, in which case split it on the board and take the first piece. A sound first piece plus honestly-filed follow-ups beats a rushed whole.
- **When an agent refuses to build something the issue names, adjudicate the kind of refusal.** "Nothing states what this is, so I shipped a verb that reports the gap" is sound engineering and merges. "This would be better done another way" is a product decision: merge only if it is reversible and recorded with the condition that reopens it, **written into the artifact where the next reader meets it** and not only into a pull request nobody re-opens. The third kind is the best outcome of all — "the issue's own Done-when offers a second outcome and the measurement says take it" — which is a completion, not a refusal.
- **`Refs #N` with a measured reason beats `Closes #N` on a bar that was stretched.** But read the decline rate in both directions: a persistent one is also a fact about **the grain the issues were written at**, and a growing share of them are written by this process. If declines cluster, write smaller issues rather than praising the honesty of the split.
- **A recorded blocker is not a measured one.** Three times in one run a milestone or an issue was parked on an assessment nobody had re-taken — a register that counted unresolved citations for several iterations, a denominator recorded as zero that was six, and a whole milestone closed as "externally blocked" six iterations before the verbs that dissolved the blocker shipped. **Re-measure a blocker before inheriting it.**
- **A milestone can run out of buildable work without being finished, and that is a finding rather than a scheduling problem.** Say so plainly, name what each remaining issue waits on, leave the epic open, and move to the next milestone rather than manufacturing work the dependency cannot support.
- **Check the board the next iteration will read.** Close any epic whose children are all done, after verifying its Done-when clause by clause against the merged tree. **Close an issue that has become an empty shell** — every deliverable dispersed elsewhere — with a table saying where each piece went; an open issue holding nothing captures the selection rule and misdirects the next pick. **If a bar names work no open issue carries, file that issue yourself.**
- **Harvest the report.** Promote anything actionable into Lessons, add findings to Open findings, and watch the net. A register with an inflow and no sink is itself a finding — and that applied to the issue board too, until the self-audit rewrite above gave it one: a self-audit finding now enters spec 13, never the tracker, so the tracker only carries work with a reader outside this repository. The net delta in the Log is how you read whether that is holding.
- **Run the product owner at the top of every run, and every fifth iteration inside one.** `.claude/agents/headwater-product-owner.md` reads the board rather than the branch, and it answers the two questions your per-iteration verification cannot: whether the run is still building for somebody, and whether it is still building the plan. `/product-owner` runs it standalone, which is worth doing after a run ends as well as during one — a run reads the board an iteration at a time and never once end to end. Do not run it in the builder's context — the agent doing the work has every reason to find the next thing to build, which is the same argument part 7 already makes for taking a second opinion from Fable.
- **The board's structure is the product owner's, and its scope is yours.** That agent closes a finished milestone, moves a misfiled issue, assigns a milestone to an eligible issue that has none, and writes the `adopter-blocking` label the selection rules read. It also closes a legacy `self-audit` issue once migrated to the register — the one exception to *it closes no issue* — and edits no Done-when. So do not close a milestone yourself and do not re-milestone an issue in passing: report it and let the next product-owner run make the change, where it lands in one report the owner can read and reverse. **Closing an epic stays yours**, and it is a different act from closing the milestone around it — an epic at zero open children is a completion you verified, and the milestone is a bookkeeping state somebody has to set.
- **Milestones run as an active set, and each one past the lowest owes a written reason.** More than one may be open, and every one beyond the lowest carries a reason on its epic saying what it waits on or why it runs in parallel. If you are about to work a milestone above one that still has open issues and no such reason, you are the party who noticed: write what you found into the report, and do not supply the reason yourself. The doctrine is stated once, in `.claude/agents/headwater-product-owner.md` under *The two rules you apply*.
- **Never run a generating verb against a checkout another session is merging into.** A second session that regenerates a corpus-wide artifact while a run merges is the silent bad merge from the other direction, and the two of you will not conflict, because blobs are compared before a merge strategy is chosen. If you meet a derived artifact stale on `main` and you do not own that checkout, say so and leave it. The session that owns it meets the same staleness at its own commit gate.
- If CI goes red after a merge, fix it in the next iteration's branch before that iteration's own work. Do not leave a red `main` behind you.
- **If an agent dies mid-iteration**, check its worktree, then **resume it rather than replacing it** — `SendMessage` to its agent id replays its transcript with context intact, where a fresh agent throws away a settled design. Both agents that died in one run resumed and finished their own work correctly, one mid-sentence. Only pushed commits survive.
- **An agent can state a write-back and not land it.** Read what it did, not what it said it would do. Check the board after every iteration, and after every resume especially.
- You may open your own pull request when a merge leaves something stale that no issue owns. Keep it small and separate.
- Never force-push. Never push to `main`. Never merge without verifying. Squash-merge when a branch's history carries a garbled commit message.
- Stop early and report if two consecutive iterations fail their own bar. Something upstream is wrong and iteration three will not find it.
- **Verify `main` itself once at the end.** Every merge was verified on its branch; nothing yet has verified their composition.

## Report

Only at the end of the run, or when a human asks.

A table of issue, pull request and result. Then the adjustments you made between iterations and why — including **what your verification caught that a report did not**, and **what it caught that turned out to be your own error**, because that is the part a reader calibrates against. If you took a second opinion from Fable, say what it changed. Then anything you would not merge again without a decision from the human. Then the ledger's path.
