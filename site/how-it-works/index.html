How it works

How Headwater checks a documentation tree, in four steps.

You declare the kinds of document you keep, and authors link the documents. Headwater checks the result and generates the indexes, the navigation and the agent context from it.

1 ·Declare what you keep

The taxonomy is one versioned file. It lists your shelves, the parts of the tree with a purpose, and your kinds, the types of document. A kind names the fields a document must declare (facets), the sections it must carry, and the links it may declare (relations).

Start from a published package and add an overlay for what is yours: your namespace, your extra kinds. You never fork the tool.

# .headwater/packages/headwater-standard/taxonomy.yml
shelves:
  decisions: docs/decisions/**
kinds:
  decision:
    purpose: rationale
    facets: [status, summary, last_verified]
    sections: [Context, Decision, Consequences]
    relations: [supersedes, governs, traces_to]

# .headwater/overlay.yml — yours
add:
  identifier_schemes.decision_id.namespace: ACME

2 ·Authors link the documents

Each document states its kind and its links in its front matter. Headwater builds a graph from them: documents are the nodes and links are the edges. A link names its target by identifier, so a rename breaks nothing. Where a relation needs both ends, as supersedes needs superseded_by, you declare one and Headwater writes the other.

Headwater also lists each file in the tree and what became of it. That list is the census, and a file that failed to classify appears in it as unchecked.

No language model takes part. The graph holds what authors declared, and each run rebuilds it from the documents.

3 ·Rules check the graph

A rule reads the graph and reports findings. Each finding names the rule, the place and the repair. The code in parentheses is an obligation: a claim Headwater makes about itself, with the rule that verifies it.

A finding is an error when its repair takes no judgment, and advisory when the repair is a rewrite. headwater check --fix applies each mechanical repair and leaves the rewrites to a person.

docs/decisions/0002-deliver-at-least-once.md:9:7 error
relation.reciprocity.missing (OB-REL-1): `ACME-DR-0002` declares `supersedes: ACME-DR-0001`, and `supersedes` requires both ends, so 0001-store-attempts-in-postgres.md owes `superseded_by`
fix (mechanical): add `superseded_by: ACME-DR-0002`

4 ·Headwater generates the rest

Headwater writes the shelf indexes, the decision lineage, the site navigation and the instruction context an AI agent reads. Nobody maintains them by hand.

headwater generate --check fails the build when a generated file and its sources differ, so a hand edit does not pass unseen.

the graph, projected:
docs/spec/README.md ← shelf index
docs/interfaces/README.md ← verb index
decision lineage ← supersedes chains
site navigation ← MkDocs configuration
agent instruction context ← per task, per shelf
$ headwater generate --check

What Headwater does not check

Headwater checks facts about documents: one exists, has a kind, governs a code path, supersedes another. It does not check what the prose claims. Take The service returns 404 on a missing key. Headwater knows which document says it, and not whether the service does.

If your tree already has a layout

Your tree does not have to match the standard paths. One key in the overlay relocates a shelf, and Relocate a shelf shows the whole move.

The tutorial takes an empty directory to a passing strict check. CI runs it against the engine, so its output blocks stay true.
