How Headwater works

A run has four steps. Declare the taxonomy, build the graph, run the checks, and project what the graph supports. This page states each one, and then it states where the reasoning stops.

Status: the engine runs, and nothing is released. The steps below describe the engine as it stands, and it checks this project's own documentation on every change.

Declare the taxonomy

A taxonomy declares what shelves exist, what document kinds live on them, what metadata each kind carries, and how documents may reference each other. All of it lives in one versioned schema. Customizing the taxonomy never means forking the tooling.

The split has a standard name, and the name is not decoration. Description logic calls the terminology a TBox and the assertions an ABox. A taxonomy is the terminology, and a corpus is the assertions. That is why the validation of a taxonomy and the check of a corpus are two different operations, rather than two halves of one operation.

Resolution merges a base package with the overlays above it, validates the result against a meta-schema, and writes a content-hashed lock. Everything downstream reads the lock and never the sources. A check result therefore depends on a hash that a reviewer can see in a diff.

Build the graph

The engine parses each file once and builds one typed graph. Documents become typed nodes, and front-matter references become typed edges. The graph, and not the file tree, is the working representation.

The obvious alternative is a separate linter for each concern, and it is the wrong decomposition. Each such tool re-walks the tree, re-parses the front matter, and re-derives what kind each document is. That is slow, and worse, it diverges. When two tools disagree about what a document is, the result is contradictory findings and an unfixable bug report.

The build also emits a census, which is every file under the corpus root and what became of each one. The census fixes the denominator before any check runs. So a document that failed to classify is counted, reported, and visibly unchecked, rather than absent.

Nothing stores the graph. Every run rebuilds it from the documents and the lock, and a cache only makes that derivation cheap. A cache that can change a verdict is a store under another name, and a test holds the difference.

Run the checks

A check is a pure function from a scoped view of the graph to a set of findings. It reads no file, it opens no socket, and it reads no clock. Everything that depends on time arrives as an injected value. That purity is what makes a result reproducible, cacheable, and safe to run in parallel.

Checks arrive from several origins. Shape checks and graph checks are generated from the taxonomy itself. A new facet or a new relation therefore brings its checks with it, and needs no code. Corpus checks read many documents at once. Document checks read the body, which is not in the graph. Plugin checks are the adopter's own, and that origin is specified rather than built. The last three are why a native engine exists at all. They are exactly what a schema language cannot express.

Every check declares its scope, and the engine enforces the declaration. A check sees one document, one edge, a neighborhood, one shelf, or the whole corpus, and it sees nothing else. That is what makes change-scoped evaluation exact, cache keys sound, and parallel execution safe.

A run has two phases, and the order answers a failure mode. Phase A classifies every file and builds the graph. Phase B runs the checks over what Phase A produced. The census is fixed first. So a document that fails to parse is counted and reported, rather than dropped from the run behind a clean result.

A finding carries a fix only when the correction is mechanical and total, which means one correct outcome derivable without judgment. Everything else carries remediation prose instead. A plausible automatic fix for a defect that needs judgment would be worse than none, because it would be applied unread.

Project

A projection is a derived artifact computed from the graph. A shelf index, the navigation for a documentation site, an agent instruction file, and a JSON export of the graph are all projections.

Three properties hold. A projection is generated and never hand-authored. A projection is checked, so a build fails when a committed projection differs from a regenerated one. And a projection is declared by the schema, within the set of projection kinds that the engine implements. So a taxonomy adds a projection of a kind the engine already has, and never a kind of its own.

A projection may be filtered, and a filtered projection says so. An export profile names an audience and a filter over facet values, and what it carries and what it withholds partition the corpus. A document held back is a loss with a declared reason, and the census reports it like any other loss. No profile may produce a view that presents itself as total.

Where the reasoning stops

The assertions here are about documents. This document exists, it is of this kind, it governs that code path, it supersedes that other document. They are not about the claims inside the prose.

The service returns 404 on a missing key is a sentence. The system knows the document that contains it, and what that document governs. It does not know what the sentence asserts about the world. Reasoning stops at the document boundary, and a promise of semantic consistency past that boundary is a promise that this project cannot keep.
