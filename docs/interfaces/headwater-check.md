# headwater check

## Synopsis

    headwater check [--strict] [--fix] [--baseline] [--no-cache] [--now <date>]
                    [--change <manifest>]
                    [--read-set <path>] [--register <path>]
                    [--format text|json|sarif|markdown | --json] [--verbose]
                    [--root <path>] [--no-color] [--no-banner]

The verb takes no operand. A word after `check` is refused, and the message names `check` as a verb the binary does not carry.

## Description

`headwater check` runs every check that the taxonomy in `.headwater/taxonomy.lock` generates over the corpus that `.headwater/taxonomy.yml` declares. It reports the census, the graph, every finding, the coverage account, the obligation register and the state of each verification. The default `text` report gives the size of the read set and not the scope of each rule. `--verbose` adds the scope of each rule and the read set, with a digest for each input, as the owner ruled on [#1990](https://github.com/headwater-ai/headwater/issues/1990). The report is one artifact in one of four vocabularies. `--format` picks the vocabulary, and `--json` is a second spelling of `--format json`.

**The `text` format renders the palette [HW-DR-0045](../decisions/0045-coloring-the-cli-and-where-the-banner-goes.md) rules on, when standard output is a terminal.** A severity word, a path, an obligation identifier and a `fix:` label each carry their own color, and the six block headings do too. The other three formats never color, whatever stream they reach. A machine reads them, and an escape sequence in JSON or SARIF is a defect rather than a courtesy. `--no-color` forces the same plain text every format already wrote before this decision.

**No format writes a control character that a document supplies.** A file name, an identifier and every other value from a document can hold a control character. A terminal or a CI log reads one as an instruction. `text` and `markdown` write each one as visible backslash text, for example `\n` for a line feed and `\x1b` for an escape. `json` and `sarif` write each one with the string escape of JSON, so a parser gets back the exact value. No value from a document opens a line of `text` or `markdown` with `::`, which a CI log reads as a workflow command. A value that opens with `::` has its first colon written as `\x3a`. A fold never puts a word that opens with `::` at the start of a line. A backslash itself is not escaped. So a name that holds `\` and then `n` reads the same as a name that holds a line feed. Read `json` when you need the exact value.

**The run is advisory unless `--strict` is passed.** A finding of any severity leaves the exit status at 0, which [spec 6](../spec/06-engine-architecture.md#cli) fixes as the default and gives the reason for.

**Two streams carry two different facts, and a caller that merges them reads a correct report as a broken one.** The report goes to standard output. The cache accounting goes to standard error, because it is a fact about the disk of one machine rather than about the corpus. `--fix` puts its account of what it wrote on standard error for the same reason. A cached run and a `--no-cache` run write the same bytes to standard output. A line about the cache on that stream is the one thing that would make the two differ.

**`--fix` writes a batch as one set, and the report a caller reads is the run after the write.** A finding carries a patch only under the [fixability bar](../spec/12-check-layer.md#fixability). So the flag decides no verdict, and it does not reach a finding that carries no patch. It does not reach a suppressed finding either, because the runner removes that finding before a writer sees the list. The verb holds each patch against the bytes that the patch names, and it reads back each result. Where the engine guessed the shape of a document wrong, the verb refuses it and writes nothing. The run opens every file of the batch before it writes the first byte. It reads each file back from the tree, and it restores what it wrote when a write fails. So a batch of corrections never lands in part.

**The verb takes every declaration from the lock and never from the package sources.** An edit to a declaration under `.headwater/packages/` or to `.headwater/overlay.yml` changes no declaration that a check reads until `headwater taxonomy resolve` writes the lock again. The verb reads the sources only to hash them, in the two paragraphs that follow, and it takes no declaration from them. Without those two readings, a test of a rule passes over a declaration that moved.

**The verb hashes each source of the lock against the lock, and reports the source that moved.** The lock records each source that it was resolved from, with a digest of its bytes. Each run hashes each of these files again. Where the digest differs, or the file does not read, `taxonomy.lock.stale` reports one error on that file. The error names the recorded digest and the computed digest. The run also compares the package, the version and the ordered source list that `.headwater/taxonomy.yml` selects now with the ones that the lock records. Where they differ, the rule reports one error on `.headwater/taxonomy.yml`. An edit that changes no resolution, such as the corpus root or the reason of an exclusion, gives no error. Each error names `headwater taxonomy resolve` as the remedy. The rule is silent where the package that the consumer names is not on disk, because the lock is then all that the root holds. It is also silent for the candidate taxonomy of `taxonomy diff` and `gate`, which no lock wrote. Where a digest pin is declared and a vendored file moved, the error also names `taxonomy.pin.diverged`, which reports the same edit against the pin. The run computes this on every run and never caches it. `.headwater/taxonomy.yml` and each source join `--read-set`'s output.

**The verb reports an agent rule that its projection's byte budget withholds.** An `agent_rules` projection declares `per_file` and `aggregate` in bytes ([HW-DR-0115](../decisions/0115-an-agent-rules-file-is-a-budgeted-pointer-at-the-copilot-instructions-path.md)). `headwater generate` writes no rule file past `per_file`, and it prunes rules until the rest fit `aggregate`. For each rule file past `per_file`, `projection.budget.exceeded` reports one warning on the path of that file. The warning names the size, the figure, and the layer to trim: the `summary` of the source document, or the figure. For each projection whose rules total more than `aggregate` after those withholds, the rule reports one warning on `.headwater/taxonomy.lock`. That warning names the projection, the total, the figure and the number of rules that the prune withholds. The caller measures the rules with the same function that `generate` prunes with, so the finding and the prune cannot disagree. The run computes this on every run and never caches it. A rule file is generated, budgeted and checked for regeneration. Its effect on agents is unmeasured.

**The verb also hashes the vendored package against the digest pin, and it takes no declaration from it.** Where `.headwater/taxonomy.yml` declares `taxonomy.digest`, each run computes the digest over the files in the package directory. It is the same number that `headwater taxonomy publish` prints. Where the two digests differ, `taxonomy.pin.diverged` reports one error on `.headwater/taxonomy.yml`. The error names the pin, the digest that the run computed, and each file that differs from the release record where a record is there. A pin that was edited and a vendored file that was edited both give this error. Where the verb finds no package directory, the error says that it computed no digest. Where nothing is pinned, the rule is silent. The run computes this on every run and never caches it. The pin file and each vendored file join `--read-set`'s output, so `headwater gate` on a later tree sees an edit to either. The error says that the bytes are not the bytes that the pin names. It says nothing about who wrote them ([HW-OBL-0115](../obligations/0115-a-pinned-digest-authenticates-the-pin-and-never-the-publisher.md)).

**A page for an adopter is held against the consumer surface the taxonomy declares.** [HW-DR-0077](../decisions/0077-the-consumer-surface-is-what-an-adopter-receives-runs-and-must-have-installed-and-it-is-a-closed-and-declared-list.md) rules that no page for an adopter instructs a file that only this repository holds. The `surface` block of the taxonomy lists those pages in `adopter_documents` and those roots in `local_roots`. `surface.local_path.instructed` reports an error for each path under a local root that such a page puts in a code span or in a code block. It reports the same error when such a page puts the path in a front-matter value. A path in a sentence of prose is not reported. A passage that states how this repository does a thing passes under a `scope=block` directive with `reason=accepted_deviation`. This is the passage "that says so" of the record. A taxonomy with no `surface` block generates no instance. The rule reads typed documents under the corpus root, and `adopter_documents` lists only such pages. `README.md` at the root is a page for an adopter, and it is untyped. The three language rules read it through the `outside_root` list of a language regime ([HW-DR-0084](../decisions/0084-a-language-rule-reaches-front-door-prose-outside-the-corpus-root-and-no-other-rule-does.md)), but this rule does not. No check of this repository holds it against the local roots, and that is a limit of this rule. The shipped package text is not a document either, so no check reads it. A token counts when it opens with a local root, with `./`, or with a shell variable such as `$ROOT/` or `${ROOT}/`. A token that is a local root with no trailing slash also counts, such as the bare directory name that a `git config core.hooksPath` line sets. A bare token does not count when it is the name of a program that the surface declares. The programs are `commands`, `prerequisites` and the `depends_on` of each integration point. So `mkdocs` in `mkdocs build` is the program of the site generator and not the directory. A word of prose that is the same as a root is not reported, because the rule does not read prose. `$HOME/` and `${HOME}/` do not count, because a path under the home directory of the user is not a path of this repository. A variable in quotes before the slash, as in `"$ROOT"/tools/x.sh`, is not reported, and that is a limit of this rule. Code inside a block quote counts. Raw HTML does not count. The rule instantiates only on a typed document that `adopter_documents` lists. Each entry of `adopter_documents` is a path pattern in the language of a shelf path. Inside one segment, `*` matches zero or more characters and `?` matches one character. A segment that is `**` alone matches zero or more segments. `surface.command.undeclared` selects its pages through the same list and the same patterns. A page that is not on the list has no instance of the rule. `archive`, `integration_points`, `prerequisites`, `companions` and `commands` are declared, and `headwater generate` renders each of them on the consumer surface page. That page is a reader and not a check. `surface.command.undeclared` reads `commands`. `surface.local_path.instructed` reads `commands`, `prerequisites` and `integration_points` only to know which bare names are programs. No check reads `archive` or `companions`.

The program exclusion applies only to a whole bare token, so `mkdocs/build.sh` counts. A bare token counts only in a shell block, as the paragraph on `surface.command.undeclared` below defines it, and in a code span. In a fenced block with a different info string, and in a front-matter value, a bare word is a value of the adopter's own configuration. So `site` in the `yaml` line `site_dir: site` is not reported. A token that opens with a local root and its slash, such as `site/docs`, counts in every block. A code span such as `` `site_dir: site` `` in a sentence is still reported, and that is a limit of this rule. <!-- headwater allow=surface.local_path.instructed scope=block until=2027-09-30 reason=false_positive note=this paragraph quotes tokens as examples of what the rule reads and instructs no path -->

**A page for an adopter runs only the programs that the surface declares.** `commands` in the `surface` block lists each program that such a page may run. It holds `headwater`, each platform prerequisite that HW-DR-0077 declares by name, and the dependencies of a declared integration point. `surface.command.undeclared` reports an error for each program that a shell block of a page on `adopter_documents` runs and `commands` does not list. The engine holds no list of programs of its own. A shell block is a fenced code block whose info string starts with one of four words: `sh`, `shell`, `bash` or `console`. The rule compares the whole first word, in lower case. So `SH` and `shell-session` are not shell blocks. A command is one line of the block, together with each line that a trailing `\` joins to it. Nothing else joins two lines, and a `\` joins only when no quote or span is open and it is not in a comment. An escaped backslash, `\\`, at the end of a line joins nothing. A `\` before a CR joins nothing, because the shell reads it as an escape of the CR. A line can end inside a quote or a span. The quotes are a single quote, a double quote and a `$'…'` quote. The spans are a pair of backticks, a `$(`, a `$((`, a `<(`, a `>(` and a `${`. Then the rule reads the programs of that line and reports an error for the rest of the block, because it cannot read it. These spans nest, and each one closes only with its own closer. A `$((` closes with `))`. A `)` inside an open `${` is text, and a `}` inside an open `$(` is text, as the shell reads them. A block that needs a quote across two lines passes under a `scope=block` directive with `reason=accepted_deviation`. In a `$'…'` quote, a backslash escapes the next character, so `\'` does not close the quote. A quote inside backticks opens nothing. A `#` starts a comment only when no quote or span is open. It must also be at the start of a line or after a blank, `;`, `&` or `|`. The comment continues to the end of the line. After `)`, `<` or `>`, a `#` is part of a word. Inside a `$(` or a `${`, a `#` is part of a word. A quote, a `\` or a `<<` in a comment has no effect. A `<<` inside quotes or inside `$(( ))` opens no here-document. The rule still reads a command that a last trailing `\` does not finish. The rule reads the first word of each command. It also reads the first word after each `|`, `||`, `&&`, `&` and `;` that is not in quotes. It also reads the first word after each `$(`, `<(`, `>(` and opening backtick that is not in single quotes. The command around such a span reads on after its closer, and the span is part of the word that holds it. So `FOO=$(pwd) npm ci` runs `pwd` and `npm`, and `echo $(date) x` runs `echo` and `date`. It skips a blank line, a line that starts with `#`, a `$ ` prompt, and an assignment such as `NAME=value` before the program. It also skips a reserved word of the shell, such as `if` or `then`, and the body of a here-document. In a `console` block, a line with no `$ ` prompt is output, and the rule does not read it. The rule compares the last segment of a path, so `./headwater` is `headwater`. A step that runs an undeclared program on purpose passes under a `scope=block` directive with `reason=accepted_deviation`. A taxonomy that declares no `commands` generates no instance, and the rule instantiates only on a typed document that `adopter_documents` lists. These are the limits of this rule. A fenced block with no info string or with a different info string is not read. An indented code block is not read. So an author tags each block of commands `sh`. A program that a different program runs, such as `sed` in `xargs sed`, is not read. The rule finds a here-document at the first `<<` outside quotes, comments and `$(( ))`. The end word is the word after the `<<` without its quotes and backslashes. It stops at a blank, an operator, `<` or `>`. So `<<\EOF`, `<<$'EOF'` and `<<EOF>out.yml` each end at `EOF`. The rule skips the body to the first line whose text, without blanks at the ends, is the end word. It finds only the first here-document of a line, so it reads the body of a second one as commands. `README.md` at the root is untyped, so this rule does not read it either. Only the three language rules read it, through `outside_root`.

**`--fix` records a verification only where the change states one.** A `verified_revision` stamp on a `source-tree` edge says that a person read the document against the file it governs. Each edge carries its own `verified_revision`, so a stamp states that a person re-read one edge, and not the whole document. So `--fix` offers the stamp on a suspect edge when three conditions hold. The run carries `--change`. The relation declares `verified_revision`. The change states the re-reading of that edge. A change states it in one of two ways. In the first way, the change re-verifies the document that declares the edge and also names the target of the edge. The change re-verifies the document when it adds the document, moves the document's `last_verified`, or names the document in a `verified` line. The change names the target when an `added` or a `prior` line names it. That line can name the target as the entry writes it, or a path that a pattern of the target matches. That path can be a file that the change deletes. In the second way, a `verified` line names the edge: `verified`, the document and the target. A moved `last_verified` does not by itself certify every edge of the document. `--fix` leaves every other suspect edge for a person, and it stamps no edge in a run without `--change`. The date does not decide, so one tree gets the same answer on every day. The target alone does not decide either. A change that edits a governed file makes every edge onto it suspect, and nobody re-read those documents. To record a stamp, re-read the document against the governed file. Then set its `last_verified` in the change that edits that file. Then run `headwater change <base> <dir>` and `headwater check --fix --change <dir>/manifest`. A second change on one day cannot move `last_verified`, because it already shows that day. In that change, pass `--verified <document>` to `headwater change`, which writes the `verified` line. When the governed file changed in an earlier change, the change in hand does not carry it. In that change, pass `--verified-edge <document> <target>` to `headwater change` for each edge that you re-read. An edit to the document does not state a re-reading by itself. Otherwise a small correction a month later would stamp edges that nobody re-read. An edge that has no `verified_revision` yet is a different case. When a change re-verifies a document, `--fix` records a first digest on each such edge of that document, whatever else the change names. A first digest re-stamps nothing that went suspect, because an edge with no stamp cannot go suspect. `--fix` stamps an entry whose target is a list under the same conditions as an entry with one target. It writes that entry in the mapping form, `to: [a, b]`, with the members in the order that the author wrote them. When the relation does not declare `verified_revision`, `--fix` writes no stamp, and the remedy of the finding gives that reason. A `verified` line can name an edge of such a relation that has no stamp. That line asked for a stamp, so the edge gets an `Info` finding with the same reason. A `verified` line that names no edge of its document stamps nothing. So a run with `--change` lists each such line, with its document and its target. Its count of documents that a `verified` line names includes the document of such a line. In a run with `--change`, the finding on a moved `source-tree` digest also says which change moved it. Either this change names what the entry reaches, or it names nothing the entry reaches and the digest moved in an earlier change. The remedy names the route that fits that case, which is the `last_verified` route in the first and `--verified-edge` in the second. A run without `--change` says neither, because it has no change to compare against.

**A run with `--change` classifies each file that a suspect `source-tree` edge reaches and the change touched.** A file is `added` when an `added` line names it. It is `removed` when a `prior` line names it and no file stands at its path now. It is `white_space` when its bytes moved and the bytes with white space taken out did not. It is `content` in every other case, which includes a prior version that did not open. To take out white space, the engine changes CRLF to LF and removes the spaces and tabs at the end of each line. Then it drops each line that is empty. Indentation is content. The engine reads bytes and no language, so the step decodes nothing. A Markdown hard break that is two spaces at the end of a line is therefore white space. That is acceptable, because the exemption below applies only when an adopter declares it. The classification changes no digest and no stamp, and the finding is the same finding. The text report lists each classified finding under `touched by the change`, with each touched file and its class. It also gives the count of touched files against the entries that the edge matches. A blocking control that declares `spares: [white_space]` leaves a finding out of its gate when two conditions hold. Each touched file is `white_space`. The digest of the edge before the change is equal to the recorded stamp. The engine rebuilds that digest from the prior bytes of the touched files and the current bytes of the other files. When a content edit landed in an earlier change that nobody re-read, the rebuilt digest is not the stamp, and the finding still blocks. The spared finding stays live at its own severity, and the report names the control that spared it. A package must not declare `spares` on a control that it ships. An adopter adds the member with an overlay `add`, and an `add` requires the key to be absent from the base. So a release that ships the key breaks each overlay that adds it.

**`--baseline` records a first digest that states no reading** ([#2016](https://github.com/headwater-ai/headwater/issues/2016)). A corpus that adopts this rule late has many edges with no `verified_revision`. The rule above stamps an edge only when a change states a re-reading. `--baseline` is the one route to a stamp that states no reading. It needs no `--change`. It writes `verified_revision` and `verified_as: baseline` on an edge when five conditions hold. The edge has no `verified_revision`. The document that holds the entry declares the edge, and not the far end. The resolver of the target is `source-tree`. The resolver states a digest, so a literal that names a directory gets no stamp. The relation declares both `verified_revision` and `verified_as`. A list target gets the stamp too, in the mapping form. With `--fix`, the run writes each stamp. Without `--fix`, each such edge gets an `Info` finding with the patch, and the run writes nothing. A second run over the same tree writes nothing, because each edge then has a `verified_revision`. When the run also carries `--change`, an edge that the change states was re-read gets a reading stamp, with no `verified_as`. Only the other edges with no stamp get the baseline. When the relation declares `verified_revision` and not `verified_as`, no stamp is offered, and the `Info` finding gives that reason. The marker stays until a reading stamp replaces the baseline. A reading stamp writes no `verified_as`, so it removes the marker. The target of an edge with the marker can move. Then the finding on the moved digest says that the recorded digest is a baseline and records no reading. The package `headwater/standard` declares `verified_as` on `governs` from 4.24.0. The owner ruled on 2026-11-22 that a baseline stamp is permitted if it stays different from a stamp that records a reading. The marker keeps that difference on the edge. A later run of `--baseline` stamps only the edges that still have no stamp, and each of them gets the marker too.

**How a `source-tree` digest is derived.** The `verified_revision` of a `source-tree` edge is not the `sha256sum` of a file, and not the git blob hash either. It is a digest of a manifest. The manifest has one line for each regular file that the edge reaches. Each line is the path relative to the corpus root, a NUL byte, `sha256:` and the `sha256` digest of the file, then a newline. The lines are sorted by path. The digest is `sha256:` and the `sha256` digest of the whole manifest. So the digest of an edge onto one file is not the digest of that file. [`headwater explain`](headwater-explain.md) prints the digest that each outbound `source-tree` edge of a document reaches now, which is the value that `--fix` and `--baseline` write. A person who re-verifies an edge without `--fix` can compute it with this command. Run it from the corpus root, and give it the files that the edge reaches:

    for f in $(printf '%s\n' <path>... | LC_ALL=C sort); do printf '%s\0sha256:%s\n' "$f" "$(sha256sum < "$f" | cut -c1-64)"; done | sha256sum | sed 's/^/sha256:/; s/ .*//'

**Nothing here reaches a network.** No crate that this verb reaches depends on an HTTP client, and the checks read the tree in front of them. The one crate with a client is `headwater-fetch`. It serves `taxonomy vendor`, and only the binary links it ([HW-DR-0075](../decisions/0075-the-vendor-verb-may-take-a-location-and-the-fetch-lives-only-in-a-crate-the-checking-loop-never-links.md)).

**A run stays linear in the size of its input** ([#1968](https://github.com/headwater-ai/headwater/issues/1968)). Five readers hold this: the YAML loader, the sentence reader, the line reader, the edge scope and the audit of a rendered report. Each case of `engine/crates/cli/tests/linear_scale.rs` runs this verb over one document that is large in one way, and holds the run inside a time ceiling. The cases are many front matter keys, many sentences in one paragraph, many links on one line, and many unresolved relation targets. The audit has its own case in `engine/crates/adapter/tests/fixtures.rs`. The [parse and census invariants](../subsystems/parse-and-census.md#invariants) name each case and the reader that it holds.

## Preconditions

**`.headwater/taxonomy.lock` is there.** `headwater taxonomy resolve` writes it, and it is written only when the taxonomy validates, so a lock is a validated taxonomy. Without one the verb prints the path it looked at, names the verb that writes it, and exits 1. Everything downstream of the load reads the lock, so this is the precondition every other one sits behind.

**`.headwater/taxonomy.yml` reads, and it names the corpus root and the exclusions.** A corpus root that no directory answers is an empty census rather than a refusal.

**The `engine` key of `.headwater/taxonomy.yml` states the engines that the corpus asks for.** When this engine is outside that range, the verb writes one line on standard error that names the range and the version of this engine. The report on standard output does not change. Without `--strict`, the exit status does not change either. With `--strict`, the run writes the report and then exits 1. A gate must not pass on an engine that the corpus did not ask for. A range that the engine cannot read stops the load, as any declaration that does not read does. [Spec 7](../spec/07-distribution-and-federation.md#consuming) states the key, and `engine/crates/cli/tests/engine_requirement.rs` holds this paragraph.

**A language regime can list paths outside the corpus root, and the census reports them on their own line.** The line reads `outside the corpus root: 4 paths, ste_house 4`, with the number of paths that each regime binds. Such a path is not a row of the census. So it does not change the count of files under the root or the coverage account. The three language rules read it and no other rule does ([HW-DR-0084](../decisions/0084-a-language-rule-reaches-front-door-prose-outside-the-corpus-root-and-no-other-rule-does.md)). The report names under that line each pattern that matches no file and each pattern that the record refuses. Each of these is also an error of `language.outside_root.refused`, so `--strict` fails on it. A symlink is never followed: a listed path that is a link, or that a wildcard matches as a link, is refused and reads nothing. A corpus that lists no such path prints no line.

**The host states a date, or `--now` states one.** The clock is read once, in this verb, before any check runs. [Spec 12](../spec/12-check-layer.md) makes the date an injected value rather than a call inside a check. One corpus, one lock and one date therefore write one set of bytes. A host with no readable clock and no `--now` is refused rather than guessed at.

**With `--change`, the manifest reads.** A manifest this engine cannot open ends the run, because a line that was dropped reads as a document that did not move. A path inside the manifest that reaches no row of the census is counted and named in the report. So a mistyped path is visible rather than absorbed. Each path of the manifest is written from the top level of the git repository, which is how [`headwater change`](headwater-change.md) writes it. When the root is a subfolder of that repository, the run removes the prefix of the root from each path before it reads the path. A path outside the root reaches no rule, and the report names it as the manifest wrote it. When the root is not in a git repository, the run reads each path as written.

**With `--change`, a file in the governed scope needs an edge when the change adds it or removes its last edge.** `relation.scope.ungoverned` reads each path that an `added` line names. It reports the path when a pattern of `anchors.<kind>.scope` admits it and no `governance` edge onto that anchor kind reaches it. The finding names the path and the pattern. The rule also reads the prior version of each document that the change carries, which includes a document that the change deletes. It reports each file in the scope that a `governance` entry of that prior version reached and that no edge reaches now. That finding also names the document. A file that the change deletes is in no scope after the change, so the rule does not report it. The rule does not read a change to the scope itself. A new or wider pattern can admit files that stood ungoverned before, and the rule does not report them. A wider scope is a deliberate taxonomy edit, and `headwater taxonomy audit` reports it. This question opens again when an adopter reports a scope edit that hid new debt. The rule uses the reach test that `headwater taxonomy audit` counts with, so the rule and the governed-scope figure agree about each path. The baseline is the change itself. The engine stores no figure and compares none across branches, because a corpus-wide fold is derived and never stored ([HW-DR-0049](../decisions/0049-a-corpus-wide-fold-is-derived-and-never-stored.md)). A file that already stood ungoverned is not reported when a change edits it. So existing debt is no finding of this rule, and a corpus that adopts it records nothing. The finding is a warning, because the remedy is a rewrite: a `governs` entry, or a narrower scope. The standard package ships its control, `CT-REL-12`, at `posture: advisory`. A corpus that promotes the control to `blocking` with an overlay `override` makes `--strict` fail on the finding. This repository does that. A run without `--change` skips the rule with the reason `change-scoped-only`.

**Each governed scope pattern matches an entry of the tree, or the run names it as an error.** `relation.scope.unmatched` reports each pattern of `anchors.<kind>.scope` that matches no entry, one error each, on `.headwater/taxonomy.lock`. The message names the pattern and the reason of the resolver, in the words that `headwater taxonomy validate` uses. One such pattern opens with a wildcard and has no literal directory before it. The resolver refuses it before any walk. The finding is an error, so `--strict` fails on it. The standard package ships its control, `CT-REL-13`, at `posture: advisory`, because the remedy is a rewrite of the pattern. The check and `validate` take one decision from one function, and there is one difference. The check counts with nothing ignored, because spec 12 keeps every version control command off the check loop. `validate` leaves out what git ignores. So a pattern whose only matches are files that git ignores passes the check and fails `validate`. Also, a top directory that git ignores counts as a tree in the check and not in `validate`. Where no tree stands beside the taxonomy, as for a taxonomy published as its own repository, the rule reports nothing. The text report then prints the notice that `validate` prints, `governed scope: no tree beside this taxonomy, so the coverage count of its 8 patterns is skipped`, below the coverage line. The JSON and SARIF reports carry no field for the notice.

| Option | What it does |

| `--fix` | Write the patch that rides with a finding, in this working tree, before the report is composed. | `--baseline` | Offer a baseline stamp on each `source-tree` edge that has no `verified_revision`. The stamp is the digest the edge reaches now, with `verified_as: baseline`. | `--no-cache` | Read and write no cache, and evaluate every instance. Standard output is the same either way, and a difference is a defect in the cache rather than a result. |
| `--now <date>` | The date to evaluate against, as `YYYY-MM-DD`. It defaults to the system clock. |
| `--change <manifest>` | The manifest of a change, which the rules that read a transition use. The flag does not narrow the documents that the run checks. | `--read-set <path>` | Write the read set of this run to a file. The report carries the same read set under `--verbose`. `headwater gate` is the reader, and it reads a file rather than a report. The flag decides no finding and moves no verdict. |

The report with the flag is the whole account, and it is the report that every run wrote before #1990. | `--no-banner` | Suppress the masthead: the line naming this binary and its version, that the root help screen alone prints. It is accepted here and does nothing, since only the root screen prints one. |

The table above is the set of flags that reach this verb. [HW-DR-0033](../decisions/0033-q33-whether-the-command-line-is-derived-and-who-a-flag-belongs-to.md) is the ruling that a flag belongs to the verb that reads it. `engine/crates/cli/tests/wiring.rs` holds this paragraph over a corpus where the verb otherwise succeeds, and `engine/crates/cli/tests/width.rs` holds the `--wide` sentence in it at both ends.

## Exit status

**0** where the run completed and no reason below applied. A finding of any severity, including an error, leaves the status at 0 unless `--strict` was passed.

**1** for each of the fourteen reasons below. There is no third status, so a caller reads the message to tell them apart.

| The reason | Where it is decided |
|---|---|
| A flag that names a value has none after it. Or `--now` is not `YYYY-MM-DD`. Or the command line holds a word this verb does not read. Or it names one target twice, as `--json` beside `--format` | the parse, before the verb is entered |
| `--format` names a target that is not one of the four | `check`, before the corpus is walked |
| `--verbose` stands beside `--format json`, `--format sarif`, `--format markdown` or `--json` | `check`, before the corpus is walked |
| The host has no readable clock and no `--now` was passed | `check`, before the corpus is walked |
| `--change` names a manifest that did not read | `check`, before the corpus is walked |
| `--fix` composed a patch and the write did not land | `fix`, before the report |
| The lock is absent, or a declaration under it did not read. Or the `imports` or `harvests` block of `.headwater/taxonomy.yml` did not read, or two of its entries name one resolver. Or the block or one of its entries is not a mapping. Or the `at` path of an entry is outside the repository root, through `..`, an absolute path or a symlink | `load`, called by `check` |
| Standard output or standard error could not be written | wherever the write is |
| The report lost a finding that no declared loss reason covers | the adapter census, after the report is written |
| `--read-set` names a file that could not be written | after the report is written |
| `--register` names a file that could not be written | after the report is written |
| `--fix` was passed and a file refused its patch | after the report is written |
| `--strict` was passed and at least one live finding is an error. Or a control that declares `posture: blocking` discharges at least one live finding, at any severity | the last reading of the verb |
| `--strict` was passed and this engine is outside the `engine` range that `.headwater/taxonomy.yml` declares | the last reading of the verb |

Two of those are worth separating. **A refused patch is not a finding**, so no absence of `--strict` softens it. The verb was asked to write and did not, and a caller who read a 0 would believe a corpus was fixed. And **the report is written before the last six rows are decided**. A run that exits 1 for one of those six still put a complete report on standard output. That holds in `text`, `json`, `sarif` and `markdown` alike.

**The first seven rows are refusals, and a refusal writes nothing to standard output.** The account of a refusal is one English sentence on standard error, under `--json` and `--format json` alike. So the property is that a refusal writes no document, and not that a non-zero exit writes none. [HW-DR-0043](../decisions/0043-q43-whether-a-refusal-under-json-is-a-json-document.md) rules it, and `a_refusal_writes_no_document_and_accounts_for_itself_on_the_other_stream` in `engine/crates/cli/tests/json.rs` holds both halves.

**A stream that cannot be written is the eighth row, and the verb does not panic on it.** A full disk and a closed pipe are the usual causes. Where standard output fails, the report is not complete. The verb then writes one sentence on standard error that names standard output and the error of the host. Where standard error fails, the report on standard output stays complete, and the verb says nothing more. In both cases the status is 1 and never 101, so a caller can tell a full disk from a defect in the engine. `the_report_survives_a_standard_error_that_cannot_be_written` and `a_report_that_cannot_reach_standard_output_exits_1_and_says_so` in `engine/crates/cli/tests/json.rs` hold the two halves.

## Environment

**No environment variable reaches this verb.** The date is `--now`, the corpus is `--root`, and the taxonomy is the lock. Six variables are read by test targets alone and reach no shipped code path. `HEADWATER_BLESS` re-records a fixture. `HEADWATER_STOCK_VALIDATOR`, `HEADWATER_SARIF_VALIDATOR`, `HEADWATER_SHA256_ORACLE`, `HEADWATER_JSON_ORACLE` and `HEADWATER_SHELL_ORACLE` each turn a reading taken by a tool outside this repository from a note into a requirement. The last of the five is `bash`, which is the only reader that can say a completion script loads. The continuous-integration job sets all five, so a lost dependency fails the job rather than going quiet.

**One variable reaches this binary, and a run of this verb reads it under `--wide` alone.** `COLUMNS` says how wide the help and the report of this verb are laid out. `engine/crates/cli/src/paint.rs` reads it, and only where the raw command line carries `--wide`. That call is the one `std::env::var` under `engine/crates/` outside a test target. The reading is held to the range 80 to 120, and a reading that is absent or is not a number gives 80. So a run of this verb that carries no `--wide` is a function of the command line, the tree and the lock. Nothing a shell exported reaches it.

**A measurement build writes more to standard error, and no shipped build is one.** The `phase-times` feature of `headwater-cli` is off by default. A binary built with it writes one `phase <name> <microseconds>` line for each stage of this verb, and a measurement script of this repository reads those lines. `release.yml` builds the default features, so no released binary carries it, and no variable or flag turns it on.

A reader who met `HEADWATER_NOW` in a continuous-integration job is reading a shell variable of that job, which the job passes to `--now`.

| `taxonomy.package` | Always | The name of the package that the corpus uses. |

### Raising the version

The current version is `1.8`. The version is a constant of the shape, and it is not the version of the engine. Two engines that write one shape write one version, so a reader does not read the shape again. The SARIF report carries `change` and `coverage` in its property bag, so this version also applies to those two members of that report.

Each version added a member, and each addition moved the minor. So an absent member says a different thing at each version. At `1.1` a report with no `change` says that the run read the whole corpus. At `1.0` it says only that the engine had no such member to write.

- `1.0` was the first shape, when `--format json` arrived. It wrote `version`, `tool`, `taxonomy`, `clock`, `coverage`, `rules`, `findings` and `read_set`. An entry of `rules` held `rule`, `scope`, `version` and `obligations`.
- `1.1` added `change`, for a run with `--change`.
- `1.2` added the account of skipped instances to `coverage`. So `"skipped": 0` says that each instance of the run reached a verdict ([#233](https://github.com/headwater-ai/headwater/issues/233)).
- `1.3` added `documents` and `unrouted` to each entry of `coverage.skips`. `documents` names the census rows that the skips of that class fell on, with the rules that skipped each row. `unrouted` counts the skips of that class that fell on no document ([#654](https://github.com/headwater-ai/headwater/pull/654)).
- `1.4` added `verified` and `verified_alone` to `change`. Before `1.4`, a document that only a `verified` line named was in `documents` and in no other count, so the counts did not sum ([#1398](https://github.com/headwater-ai/headwater/issues/1398)).
- `1.5` added `compared` to the entries of `rules` for `link.identifier.mismatch` and `link.fragment.unresolved`. A rule that reports nothing is silent over links that all pass. It is also silent over a corpus with none of its links, and `compared` tells the two apart ([#1347](https://github.com/headwater-ai/headwater/issues/1347)).
- `1.6` added `unstated` to `change`. Before `1.6`, a `verified` line whose target its document does not govern was in no member. A line whose document no row holds was in `unmatched` only as its document path ([#1631](https://github.com/headwater-ai/headwater/issues/1631)).
- `1.7` added `blocked_by` to a live finding that a `posture: blocking` control discharges. Before `1.7`, a report did not say why a strict run over a corpus with no error failed ([#2015](https://github.com/headwater-ai/headwater/issues/2015)).
- `1.8` added `touched` and `spared_by` to a live `relation.target.suspect` finding of a run with `--change`. Before `1.8`, a report did not say which governed files a change touched, or whether a change moved only white space ([#2100](https://github.com/headwater-ai/headwater/issues/2100), [#2028](https://github.com/headwater-ai/headwater/issues/2028)).
